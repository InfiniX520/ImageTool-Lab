## 1. 本轮结论

JpgPng 已有可用的下载主线和适合当前用户的操作方式，但核心下载能力与成熟开源项目高度重叠。继续开发应按用户收益取舍：提高收藏结果的可信度，减少重复查询和维护负担，保留已认可的界面与渐进收集方式。自研代码数量、功能按钮数量和开源星数都不是目标。

建议先完成“记录能反映磁盘现状”和“收集结果能说明覆盖范围”，同时做小范围的成熟组件接入验证。是否采用 gallery-dl 由接入收益和验收结果决定，不因既有投入拒绝，也不预先决定整体替换。

依据是[三项目审计](../../audits/2026-11-11/README.md)、当前源码和本轮官方资料复核。审计中已复现的问题仍未修复。当前设计没有把历史测试通过当成新设计已实现。

## 3. 用户需求作为取舍依据

1. 原图质量与完整保存优先；原图失败要说明原因，不能用预览或缩小图冒充成功。
2. 默认逐步收全关注画师历史；同时保留新作和指定画师，发现新画师后容易加入。
3. 保留原始格式、多页、可叠加筛选、暂停续跑和可读下载名单。
4. 下载界面不取缩略图；整理画师时独立、按需看多件作品。
5. 性能以请求、磁盘、内存、界面响应的实测为准；不能靠关闭校验取得成绩。
6. 保留相对路径、现有 Python/Tk 入口；不为美化另建 Node、浏览器框架或模型环境。
7. 保留已认可的白蓝视觉、细线与适度阴影；当前重点是状态清楚、操作方便。
8. 允许替换不合适的结构，但不默认清空数据库、重下整个图库或覆盖用户文件。

## 4. 哪些已有，哪些需要补强

| 项目 | 现状 | 本轮判断 |
| --- | --- | --- |
| 原图、多页、临时文件和崩溃恢复 | 已有页规划、结构检查、摘要、prepared/发布/完成协议 | 保留，扩大有针对性的异常验证；不重写通用 HTTP 框架 |
| 持久化与断点 | 新 SQLite 单库、批次和游标已存在 | 扩展现有账本，不引入第二套完成事实或常驻数据库服务 |
| 完成记录的再次使用 | 审计复现删图/等长替换后仍复用 | 第一优先级；属于旧设计“普通去重信任记录”的局限，不只归责实现 |
| 图像深度验证 | JPEG 等主要是结构检查，不是完整像素解码 | 明示验证等级；评估一个成熟解码依赖的价值，不自己写完整 JPEG 解码器 |
| 关注历史与增量 | 已有快照、分页、稳定 ID、预算与未知状态 | 强化结果说明及可见集合对账；不是新增一套关注调度器 |
| 筛选 | 通用 FilterSpec 当前只有最低收藏和排除 AI；来源各有参数 | 先做解释与方案保存，再按字段证据扩展；不能把搜索关键词当全来源标签过滤 |
| 日志和 UI 性能 | 已有有界队列、轮转、增量刷新及历史长测 | 先量化新核验带来的开销；没有证据就不再改线程模型或换 UI 框架 |
| 整理 CLI | E1-2 已交付，真实多图分类和批量分组仍待做 | 保留独立支线；账号整理不绑到下载启动流程 |
| 依赖与发布 | 审计有共用依赖公告匹配，项目依赖缺乏完整锁定 | 单独、可回退地维护共享环境；设计阶段不直接升级 |

## 5. 成熟项目如何借鉴

| 参考对象 | 值得采用的能力或方法 | 需要保留的边界 | 本轮建议 |
| --- | --- | --- | --- |
| gallery-dl | 来源提取与下载分层；Pixiv 网页/App 可见集合对照；批量输入、元数据与配置组织 | 默认降级、Range/发布问题、提取循环预算、archive 与本地文件一致性仍需评估 | 优先做只读来源对照，再决定是否接入提取层；整套下载替换为备选 |
| PixivUtil2 | 缺失文件记录维护、画师名单、Pixiv 特有归档选项 | 部分缺失清理不等于全库内容验证；OAuth 日志和默认校验问题不能带入 | 借鉴维护入口及使用流程；不直接并入其数据库或全部依赖 |
| yt-dlp | 来源、传输、后处理阶段分离，结构化程序接口、进度与归档语义 | 主业是音视频；没有证据支持直接替代本项目 Pixiv 关注原图链路 | 作为架构参考；当前不安装、不接入视频功能 |

gallery-dl 的补漏和 JSON Lines 选项见[官方配置文档](https://gdl-org.github.io/docs/configuration.html#extractor-pixiv-sanity)。选项存在不等于运行时内存、错误或预算契约适合嵌入，需结合固定源码判断。PixivUtil2 的实际缺失检查见[固定源码](../../../../references/pixiv_downloaders/2026-11-11/PixivUtil2/PixivDBManager.py)。

### 5.1 yt-dlp 的定位

yt-dlp 是音视频下载工具，适合围绕视频格式、媒体分片和后处理组织任务。它的“最佳质量”仍以网站可提供的版本为前提。当前官方支持列表未列出 Pixiv 插画收藏专用提取器；通用媒体链接处理能力不能证明它支持关注画师历史、多页原图或网站分组。[官方说明](https://github.com/yt-dlp/yt-dlp)、[支持列表及其适用限制](https://github.com/yt-dlp/yt-dlp/blob/master/supportedsites.md)

对本项目最有用的是学习接口边界：传输完成之后还有验证、发布与记账，UI 不应从一条人类可读日志猜“全部成功”。若以后另有视频归档需求，再评估 yt-dlp；合并媒体通常涉及 FFmpeg，完整 YouTube 支持还有其相应依赖，不能算当前图片项目的免费附加功能。没有为本轮研究安装这些组件。

本轮只核对 yt-dlp 官方文档及适用范围，没有对其做与前三项目等量的源码、依赖及动态安全审计，也不声称其已通过安全验收。

## 6. 决策记录

| 编号 | 建议决策 | 原因及代价 |
| --- | --- | --- |
| D01 | 新默认完整性策略：本批涉及的已有页经完整摘要复核才标“本批已核验” | 能发现等长替换；增加读盘。只对触达页做、有界、可暂停，不启动全盘扫描 |
| D02 | 提供显式快速复用模式，但标“按记录跳过/快速检查” | 满足重复扫新性能需求；它不证明内容未变，不继承严格核验标签 |
| D03 | 保留交付历史，另记文件当前状态与核验时间 | 文件丢失不抹掉当时下载成功的事实；需要一次账本迁移和查询调整 |
| D04 | 核验默认只检查；补齐为明确操作，可保存“该方案自动补缺失”偏好 | 避免用户主动删除后每次偷偷下回来；批量操作无需逐件弹窗 |
| D05 | 来源查全、符合条件、文件齐全分开表示 | 能区分筛掉、查不到、未支持、损坏；比单一“完成”多一点状态设计 |
| D06 | 优先验证 gallery-dl 提取层收益，暂不定整套替换 | 可分担接口维护且保留质量协议；必须解决预算、取消、错误和版本契约 |
| D07 | 类型化筛选、任务快照、可读解释；不引入 eval 表达式入口 | 避免配置代码执行和复杂规则负担；高级用户自由度有所限制 |
| D08 | 核验和来源实验均复用现有资源所有者，默认不引入新依赖 | 先修可靠性；深解码另行评估一个有明确收益的组件 |
| D09 | 样图整理、动图原件、视频下载分别决策 | 防止为了功能齐全扩大默认请求、依赖和 UI 复杂度 |

D01/D02 是对旧“只信记录”策略的实质调整。严格模式仍只能证明检查时文件与已保存摘要一致；不能证明远端就是作者最初上传的源文件，也不能保证检查后的外部修改不会发生。

## 7. 优先级与阶段

“待实施”不是已授权自动执行所有未来方案。本轮产物供逐步确认方向；接续先做 U1 的小闭环，不并行展开全部功能。

| 阶段 | 工作项 | 完成标准 | 状态 |
| --- | --- | --- | --- |
| U0 研究与设计 | 审计承接、原设计对照、成熟工具评估、验收定义 | 三份设计、证据索引、文档及基线核验 | 本轮完成 |
| U1 可靠性 | U1-A 文件复核/补缺失；U1-B 共用依赖维护；U1-C 质量等级及深解码评估 | 删除/篡改/目录离线不会误报完整，回退不丢资料；依赖单独验证 | 待实施；A 与 B 为独立批次 |
| U2 收集体验 | U2-A 覆盖摘要；U2-B 筛选解释、保存方案、离线重评估；U2-C 请求和读盘基准 | 常见未完成原因可直接处理；条件变化不漏旧候选 | 待实施 |
| U3 成熟组件试验 | 固定稳定版来源对照，必要时做提取适配原型 | 同条件结果、资源/预算/取消/升级证据，明确采用或放弃 | 待实施；不替换默认入口 |
| U4 按需拓展 | 动图原件、更多筛选、E1-3 多图分类小样 | 各自独立验收；不把未选扩展算欠缺的主线任务 | 候选 |

U1-A 优先做“选一位画师或本批 → 核验 → 生成差异 → 补缺失”的闭环。它对当前质量问题有直接收益，也适用于以后更换引擎。U3 的公共资料研究可以继续；真实对照在相关传输依赖修复并验证后开始。

## 8. 本轮暂不做

- 重写整个应用、换 GUI 框架、常驻 Web 服务、通用插件市场。
- 默认启动全库扫描、每件作品重复查详情、每次续跑重复同步全部关注。
- 图像转码或嵌入元数据作为收藏原件的默认步骤。
- 相似图模型、向量库、自动判定“这位画师不值得关注”。
- 为多站点而接入所有 gallery-dl 提取器，或因 yt-dlp 强大而增加视频入口。
- 同时维护三个下载引擎、三套完成账本和两套活动 UI。
- 立刻删除 legacy 入口；其退出条件是使用范围、回退需求和数据路径都核清。

## 9. 尚待测量或讨论的选择

1. 严格触达页核验在实际磁盘上的成本；如果读盘明显拖慢，先调整缓存和调度，再讨论默认策略，而不是暗中改成弱检查。
2. 是否引入一个成熟解码库；需核对格式、资源、包大小与现有环境，不用“零依赖”当成继续手写所有解析器的理由。
3. 网页补漏当前账号可获取多少新增作品，以及额外请求与维护成本；不能仅凭源码功能决定接入。
4. 标签、尺寸、类型等筛选按实际使用选择，不一次性铺满高级参数。
5. 动图原件和多图分类的先后；当前静态收藏可靠性优先。网站上的人工分组修改必须继续受保护。
