## 3. U1 验收矩阵

### 3.1 文件和记录

| 场景 | 必须看到的结果 |
| --- | --- |
| 已完成页仍为原始字节 | 严格模式核验成功，不重复下载；记录核验时刻与策略 |
| 已完成文件删除 | 新批次不声称本地完整；给出缺失结果和可选修复 |
| 等长替换，含保留 mtime 的情况 | 严格模式摘要不符；快速模式的局限如实显示 |
| 截断、损坏 PNG/JPEG、HTML 假图 | 当前规则能识别的故障失败；深解码范围另外标明 |
| 根磁盘拔出、根权限失败 | 根不可用，不将全部页登记为缺失或启动批量重下 |
| 根映射变化、重解析点、路径边界替换 | 拒绝越界/过期观察，不读取或覆盖未知目标 |
| 核验期间修改或替换文件 | 不稳定结果保留待核验，旧 revision 不覆盖新结果 |
| 同任务恢复、跨任务复用、同批重复出现 | 结果语义一致，单批相同页不重复读/占名额 |
| 来源确认后、核验前进程退出 | 已持久化核验待办可恢复；候选不丢、游标不越过未确认事实 |
| 修复时路径被他人占用 | 保留现有文件，转冲突，不直接覆盖 |
| 修复下载/发布/数据库提交各边界退出 | 幂等恢复，新旧成功事实与文件都保全 |
| 有意移除后再次枚举 | 遵守该范围排除意图；撤销后可补齐 |
| 无可信历史摘要的旧文件 | 不伪造历史匹配结果；纳入/重新下载为明确动作 |
| 作品页数或可靠来源版本变化 | 新代次/待复核，不复用旧“全页完成”掩盖新页 |

测试要从实际协调器、仓库和交付边界进入，至少覆盖一条真实 Tk 控件到后端的离线闭环；不能全用 mock 相互证明接口名称相同。失败测试及修复前复现保留，不只保留最终绿色截图。

### 3.2 依赖维护

U1-B 是共享环境维护，不与功能改动混成一次不可回退提交。实施时重新读取安装规则、确认实际版本及维护者公告，保留包清单/来源与回退材料；审计日期的公告匹配不代替届时核对。

先检查其他在用项目是否运行；不在它们运行时原地替换其依赖。候选升级要做版本解析、模块路径、`pip check`、相关网络传输/证书离线样例及各受影响项目必要的无业务副作用检查。若无法保证共享环境可安全维护，先安排维护窗口或副本验证，不偷偷另建一套永久环境。

审计中的依赖风险尚未关闭。状态需分别记录“公告匹配”“升级完成”“兼容检查通过”，不能只把 requirements 下限改高就记已修复。

### 3.3 深解码候选

采用合法样本、截断/内部损坏、巨幅、超多帧、解码超时和取消样本。比较原图前后摘要完全相同；不把能生成缩略图当作所有帧验证。若选择进程隔离，验证内存限制、工作进程退出、句柄与临时文件归属。没有完成上述条件的格式保持较低验证等级。

## 4. U2 性能和筛选验收

### 4.1 性能测量方法

使用同一机器、DPI、存储根、版本和相同本地合成输入。分别测新下载、全是已有图、少量缺失、部分变动、元数据未知多、重复候选多、日志突发等场景。基线与候选轮换运行，预热/冷缓存/热缓存单独记录，至少多次重复，不以最快的一次作结论。

| 指标 | 记录内容 | 初始目标/判断方式 |
| --- | --- | --- |
| UI | 点击/切页/暂停反馈 p50/p95/max | 沿用 p95 ≤100 ms 目标，新增核验不得造成持续 500 ms 冻结 |
| 读盘核验 | 页数、GiB、墙钟、CPU、磁盘吞吐、等待下载时间 | 报实测，不承诺无成本；同策略比较，禁止弱化检查凑成绩 |
| 来源成本 | 各端点实际尝试、重试、详情、字节与命中缓存 | 重复出现不重复补查；已知排除不为未知字段发请求 |
| 持久化 | 写队列、提交耗时、读事务持续时间、WAL 大小 | 沿用有界容量，核验不占长写事务 |
| 内存与资源 | Python/子进程合计 RSS、私有内存、线程/句柄、队列峰值 | 随作品总量不出现未解释的线性增长；必须测包含适配器的总量 |
| 暂停/关闭 | 控制反馈到安全停止、最后确认状态 | 反馈及时；阻塞系统调用超时如实显示，不假装已退出 |
| 名单 | 原历史计数、新批次核验/新增/待处理 | 不因重试、核验或读回重复累计成功 |

旧设计已有两小时离线长测证据；新改动先跑相关功能和资源验证。只有加入新资源所有者或出现持续增长疑点时，才安排新的针对性长测，不能每次文档更新就重跑两小时。

### 4.2 筛选与覆盖样例

- 各条件关闭、单开、AND 叠加；已知拒绝优先于未知；缺字段不变成 0/false。
- 方案保存、重启、切换来源草稿、运行任务的不可变条件；原合法用户值不被新默认覆盖。
- 条件放宽补查旧过滤范围、条件收紧不删既有图；收藏数变化有观察时间。
- 标签原文、Unicode、大小写、包含/排除同时命中、字段未知；不允许注入代码。
- 多页尺寸条件若实施，明确全部页/任一页；不能只用封面尺寸代表所有页。
- 关注列表不完整、画师改名、新关注/取消/重新关注、跨账号、分页重复、页内插入删除、锚点丢失。
- API/网页集合差异、权限变化、作品删除与扫描时间差；失败接口不伪装成空集合。
- 预算在页中用尽仍可续；范围未穷尽时不展示“全部收齐”。

## 5. U3 外部组件对照方案

### 5.1 先离线，后有界真实样本

第一层用固定元数据和本地 HTTP 响应比较归一化结果、错误、分页与预算；第二层使用同一已授权账号的有限作品与画师做只读对照。设计阶段不执行真实账号请求，不读取凭据。

未来真实试验的建议初始总预算：不超过 2 位画师、20 件指定作品、合计 60 次图片传输尝试、100 次元数据请求尝试、512 MiB 图片正文及 15 分钟墙钟，任一到达即停并保存未决范围。总量包含所有对照分支及重试，不能每个工具分别拿一份预算。样本过大时缩小样本，不能静默突破预算；仅用于小样正确性判断，不声称统计代表所有作品。

访问认证失败、验证码、明确限流或重复异常时停止；不为对照切账号、换代理或循环探测。普通失败如实记入，不隐藏失败后只报告成功样本。涉及浏览器会话时确认对应账号并沿现有授权边界处理，报告不含令牌、Cookie 或带秘密的 URL。

若只有来源对照，禁止图片下载；若做图片字节对照，使用实验目录与独立测试库，正式图库/完成账本不参与写入。下载所需元数据可在已授权范围内缓存，记录观察时间和缓存命中。

### 5.2 对照分两组

| 组 | 用途 | 不混淆的条件 |
| --- | --- | --- |
| 指定同一作品/原图集合 | 比较原图字节、页数、失败类型、请求成本和恢复 | 作品集合与资源版本要相同；同文件无需反复向服务器下载制造压测 |
| 同一画师可见集合 | 比较来源遗漏、类型覆盖、接口差集与额外请求 | 集合可能随时间变化；不能把工作量不同的总时间当吞吐排名 |

原图正常样本比 SHA-256/字节数/页数与来源身份；不一致先查 URL、版本、时间和品质策略。一个工具接受、另一个拒绝的样本必须解释，不能单纯把接受率高判定更好。

### 5.3 接入硬门槛

| 门槛 | 不通过时的选择 |
| --- | --- |
| 原图政策和所有所选页正确 | 不替换默认下载路径 |
| 请求与墙钟有界，取消可控 | 不嵌入常驻主线；最多保留受监督小样工具 |
| 错误可识别，缺终态不报完整 | 补充最小可靠协议或放弃该接入方式 |
| 来源结果、路径和配置受控 | 拒绝任意外部执行/越界，不以用户不会乱配为保证 |
| 内存/队列有界，日志不含凭据 | 先修适配，不把问题推给 Tk |
| 本地库与第三方状态只有一个业务事实来源 | 不实行双写完成账本 |
| 至少对选定版及一个相邻可用版做契约回归 | 无法承担升级成本则固定实验用途，不宣称长期稳定接口 |
| 有具体减少维护或补齐能力的证据 | 只保留借鉴，不为“使用了开源”强行引入依赖 |

如果实测发现直接使用 gallery-dl 的配置和命令已满足用户日常需要，也允许缩减 JpgPng 的长期维护范围，仅保留确有价值的组件；没有“必须保住全部自研”的预设。反过来，接口适配成本超过收益时维持现有主线也合理。

## 6. 发布与回退

1. 每个实现批次先记录工作树与相关源码摘要，不复用本轮基线冒充未来起点。
2. 修改生产符号前按 AGENTS 做影响分析；已有未提交修改保留，不 reset，不盲目提交。
3. 先在隔离的合成图库/账本验证迁移与异常；生产扫描与修复由明确范围控制。
4. 配置/库升级备份使用一致性机制。开启新结构前安全停止同库写入，验证最低读写版本。
5. 逐项发布，既有启动入口与认可的 UI 连续可用；新引擎先为实验，不自动全量接管。
6. 回退先保全新版本产生的文件、核验观察和任务事件。旧版本不认识新 schema 就拒绝写入，而非强行打开。
7. 业务待办、原件、名单、备份及认证不纳入临时清理；清理只针对带所有权清单的实验产物。

迁移、安装、修复和真实测试是不同动作，分别留证据；不能一个“成功”状态覆盖全部。
