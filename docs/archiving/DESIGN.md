# 归档详细设计

版本：v1，2026-11-11。本文是待实现协议；用户事实及优先级以 [README](README.md) 为准。

## 1. 端到端流程与职责

```mermaid
flowchart LR
    S[选定本地文件或新下载成果] --> P[盘点与空间计划]
    P --> B[冻结输入并生成独立加密包]
    B --> L[本地解包与成员摘要核对]
    L --> R[分组恢复数据与可移植目录]
    R --> U[用户通过夸克官方客户端上传]
    U --> D[从夸克取回到独立目录]
    D --> V[完整包摘要与解包验证]
    V --> C[保存归档证据和位置]
    C --> E[生成本批可释放清单]
    E --> X[用户明确执行空间释放]
```

暂停/重启可以发生在每一步；只有已持久化事实可作为下一步前提。上传和下载交给现有官方客户端；我们的程序不假定拥有可用的夸克 API。首版人工传输和本地自动核验可以独立完成，不把全面云端自动化作为上线条件。

职责落在现有单写账本、短查询和 Tk 主线程之上，新增一个有界归档 I/O 所有者及受管工具进程。每次最多一个归档工作批次、一个封包或修复进程，不给每个作品建线程。与下载同时运行时共享磁盘容量预算；若无法证明兼容，首版归档写入与下载写入串行，仍允许查看记录。

## 2. 保存事实和状态

### 2.1 不使用一个“完成”代替全部事实

保存以下独立维度，而不是一个不断膨胀的状态枚举：

| 维度 | 状态示例 | 说明 |
| --- | --- | --- |
| 下载来源 | original_received / observed_existing / legacy_unverified | 归档不伪造原图来源证明 |
| 本地 | present / changed / unavailable / deliberately_evicted / absent_unclassified | 文件不存在不自动等于故障，也不自动等于已归档 |
| 归档对象 | planned / building / locally_verified / sealed / failed | 封包字节和内容是否验证 |
| 远端证据 | not_submitted / user_reported_uploaded / user_returned_verified / adapter_readback_verified / access_failed | 人工与自动来源证明分级 |
| 恢复保护 | none / partial_damage / whole_largest_pack / degraded | 记录实际可恢复块数及演练结果 |
| 空间释放 | not_eligible / eligible / prepared / released / conflict | 独立操作，不能由上传事件直接触发 |

推荐界面用语：“已上传，待回读”“人工取回，内容核验通过”“已归档，本地已释放”“远端待复查”“位置待确认”。不得把 `user_reported_uploaded` 显示为已验证。

历史下载事件保持不变。云端出错更新归档可用性，不抹去过去的下载成功；本地释放不减少历史成功数。需要当前本地文件的“打开图片”与可以定位归档包的“找回原件”是不同动作。

### 2.2 与下载去重连接

默认目标为“保存一份符合条件且可追溯的原件”，允许该原件已归档。已有页命中时先查保存形态：

- 本地有效：按该任务策略复用。
- 已有合格归档及主动释放事实：计 `skipped_archived`，显示归档位置和核验日期；不从 Pixiv 重新下载，也不每次从云端回读。
- 用户说已转存但没有核验证据：显示“历史转存，未核验”，保留其意图；不自动冒充当前完整，也不自动重下。用户可选保留历史信任或加入归档复查。
- 缺失且没有转存/排除意图：列待处理，由用户选定位、恢复归档或重新下载。
- 归档最近访问失败：保留旧证据，显示风险；只有用户指定修复范围后才取回或重下。

“需要本地副本”的任务另设明确选项，优先从归档恢复，再按用户选择考虑远端原图。不能让收藏策略变化暗中触发数百 GB 的下载。UI 的“本地齐全”和“已保存到归档”分别计数。

## 3. 文件清单、输入一致性与分包

### 3.1 输入和归属

入口接受用户选择的本地根、指定画师/任务的已完成成果，或明确选定的旧资料副本。只对这个范围盘点，不遍历整个工作区。排除当前写入中的下载、归档输出、诊断日志、数据库和凭据；用户选择混合目录时先列入选/排除清单。

拒绝符号链接、junction、其他可能越界的重解析点，以及不受支持的网络文件系统；硬链接要识别同一文件身份，不能把删除一个名字当释放多份磁盘空间。Windows 路径需处理大小写碰撞、保留设备名、ADS、尾部空格/点、长路径和 Unicode；归档内部只用受控相对路径，外部标题不作命令或任意路径。

新下载优先关联 artifact 的摘要和质量证据。现存旧文件没有可信摘要时，在本次冻结输入上计算 SHA-256，并标明 `observed_existing`、观察时间，不升级为“当初下载已验证”。有意外摘要差异时隔离为冲突，不重新定义正确值以消除错误。

### 3.2 输入冻结

封包前按清单复制本包输入到受管 staging，复制同时算摘要，并核对源前后文件身份/大小/修改状态；完成后验证 staging 与期望摘要。读取期间变化、被锁或权限失败的文件使本包计划待处理，不忽略后继续宣布全量完成。

不把硬链接 staging 当不可变副本。封包只读取固定 staging，工具成功后再核对解包内容，防止异步修改或不同进程读到不同字节。企业文件保护软件若导致读取差异或阻止访问，保留错误，不关闭/绕过保护软件。

每包 staging 可在本地包验证后释放，但必须确认原图仍在或已由后续流程保全；源原图不因 staging 生命周期自动删除。中断半包保留为未完成产物，不能覆盖已封存同名包。

### 3.3 包划分

使用稳定随机批次 ID 与递增包序号，例如 `a_<batch>_<seq>.7z`，不把成人标签、作品标题、账号写到公开包名。清单保留作品/页和原相对路径映射；包顺序确定后冻结。

目标约 2 GiB，尽量让一个作品的所需页同包，但不按单个画师无限增大。单件作品或单文件超过目标时单独成包，并在计划中显示大小；不隐藏切断图片。封包后实际大小超过该远端已验证能力时，在上传前重新规划新包，旧包保留待处置，不改变已提交包的字节。

独立包不用分卷选项；不同包之间没有解压依赖。成员内非固实是恢复便利性选择，不是“单包绝不坏”的保证。新文件只追加新批次，不修改历史封存包。相同明文再次加密可能产生不同密文摘要，包身份以一次封存的具体密文字节为准。

## 4. 可移植格式、目录与密码

### 4.1 包内、包外清单

| 文件 | 内容 | 保管 |
| --- | --- | --- |
| 每包 `manifest.json` | 格式版本、批次/包 ID、成员相对路径、size、SHA-256、作品/页关联、来源证据等级 | 在加密包内部；不包含包自身摘要 |
| 分组 `group.json` | 包的密文摘要/大小、恢复对象摘要、编码参数、所需成员、实际恢复能力 | 随加密控制包保存；本地保留可读受保护副本 |
| `catalog.jsonl` | 作品/页 → 归档包、内部路径、密码版本引用、远端位置；分段版本 | 加密控制包、本地目录与每包内可重建信息 |
| `RESTORE.txt` | 通用恢复步骤、格式与工具来源、摘要算法、版本兼容说明 | 不含秘密；每组都有，不依赖 JpgPng 才能阅读 |
| 脱敏外层 inventory | 不透明对象名、字节数、SHA-256、控制包标识 | 本地及云端，用于先校验密文和定位控制包 |

自引用禁止：包内清单不能保存包自身最终摘要；控制包也不声明自己的最终密文摘要。最终摘要放外层 inventory 与本地账本，inventory 不包含自身摘要；可以在另一个小型恢复记录中保存其摘要。

恢复不得只依赖一个总目录文件。每包 manifest 足以解释自身成员；总目录损坏时可逐包重建。标题/标签等私密元数据不放明文远端索引；本地可读目录也属于业务资料，不进入通用日志或公开报告。

控制包导出的是已提交事实快照，记录事件水位。它自己的上传/回读证据在生成后写入本地账本及后续快照，不为了让文档包含自身验证而无限递归生成控制包。无原账本恢复时可重新完整核验各包，建立新的当前证据，不要求拥有旧回读事件才能解压。

### 4.2 格式与工具

主候选为成熟 7z/AES-256、文件名加密、非固实、存储或低压缩；完整保留图片字节、扩展名和有用时间信息，不嵌入元数据重写图片。最终选择还需工具版本、包大小、安全公告、读取兼容性和密钥通道测试。

备选是 RAR5 及其恢复能力；恢复记录主要用于部分损坏，与独立整包丢失保护不同。首版只选一条经过验证的封包路线，不同时维护两个生产后端。[RAR 官方恢复说明](https://www.win-rar.com/recovery-record.html)

2026-11-11 的有限只读工具检查：PATH 中发现一个位于 `esafenet/cobra docguard client` 目录的 WinRAR；常规 7-Zip/WinRAR 安装路径未发现对应文件。**没有执行该程序，不把其他软件附带的可执行文件当作本项目可信工具，也不修改该软件。** 这不是全盘搜索或“机器绝对没有其他压缩软件”的结论。

计划复用现有 Python 标准库；必要时增加少量项目内便携工具，经官方来源和摘要/签名核验，不增加系统服务、全局 PATH 或 Node 环境。安装/获取可执行工具是以后独立动作，遵循[安装规则](../../../给AI的安装守则.md)，本轮没有安装。

### 4.3 密码输入和恢复

密码只由用户在本地受控输入，聊天、命令行参数、日志、配置导出、异常栈和截图不得含明文。账本仅存 `key_ref` 与版本，不存密码。Windows DPAPI 如用于本机便利，只是可选缓存，不能是唯一恢复方式，否则重装系统会失去解密能力。

归档方案启用前，用户应在密码管理器或独立离线介质保留密码恢复材料，并用该恢复材料实际解开测试包。不要将密码仅保存在它所解密的那个包内，也不要把密码放在同目录明文说明里。

**安全密码交接是 A2 硬门槛。** 不假定 7z 在 Windows 上一定能通过重定向 stdin 安全接收密码；需验证具体工具版本、控制台行为、取消与输出。在没有可靠交接方法时，使用用户在官方工具交互界面输入密码的半自动小样流程，不退回把真实密码拼进 `-p...` 进程参数，不自研加密替代。

真实密码不得用于日志泄漏探针；使用专门测试口令检查进程参数、输出和报告。无法验证安全输入时自动封包阶段保持待实现，清单和核验功能仍可继续开发。

## 5. 恢复数据设计

对已封存的**加密包**生成 PAR2，避免纠错文件暴露明文图像内容。每组默认最多 10 个独立包，起点 15% 冗余；记录实际块大小、数据块数、完整恢复块数与对象摘要。纠错文件也是受保护的归档对象，必须上传并完整回读核验。

分两种明确能力：

- `partial_damage`：修复在实际恢复块能力以内的损坏，不能保证整包丢失可恢复。
- `whole_largest_pack`：本组最大包全部丢失时，仍有足够完好的恢复块及必要描述信息；需通过同参数的破坏副本演练。

若某包占用 `ceil(size/block_size)` 个块，目标至少需要对应数量的完整恢复块，并为额外损坏留明确余量。损坏按块计：分散的单字节损坏可能消耗很多块，不能把 15% 解释为任意位置/形态下都能恢复 15% 字节。

尾组只有少数包时，15% 往往不足恢复最大整包。规划器必须展示这一点：按目标提高冗余，或由用户明确选择仅局部损坏级别；不静默标整包可恢复。只有一个包时要求整包丢失保护可能接近额外一整份数据，成本必须如实显示。

修复只在隔离副本/工作区内进行，先核对其余输入密文摘要，再输出新恢复文件；成功后核对完整包摘要与成员摘要，不能只信工具“repair successful”。好包、原损坏包和失败证据在确认前不覆盖。所有包及恢复数据同时无法访问时，该方案没有恢复能力。[PAR2 官方机制](https://github.com/Parchive/par2cmdline)

## 6. 空间与性能预算

当前输入规模以用户估计为准，执行时读取目标卷实际余量；所有临时路径相对项目或显式资料根，不放系统临时目录、不依赖当前工作目录。

规划计算“额外需要的空间”：冻结副本、加密包、恢复数据、当前回读包、当前解包输出、控制资料和安全余量。原本已占用的源文件已反映在 free space，不能再次误算为额外分配；各阶段并存关系必须计入。

保守举例：20 GiB 冻结输入 + 约 20 GiB 加密包 + 约 3 GiB 恢复数据 + 约 4 GiB 单包回读/解包 + 10 GiB 余量，约需 57 GiB 额外空间，实际按文件和格式计算。逐包冻结可降低峰值；单文件超大时重新计算。修复演练另算整组工作空间，不能复用封包预算冒充足够。

每次开始复制、封包、回读、解包、修复前重新检查空间；下载主线和其他进程消耗空间时允许暂停。空间不足不自动删除原件、未核验包或其他批次。由用户选择减小批次或清理明确可释放对象。

哈希与归档读取均流式，内存有界；清单大时从 SQLite 分页，不把全部图像载入内存。UI 展示当前阶段、已处理字节、预计额外空间、等待用户操作和失败原因。网络流量充足意味着可以做全量回读，不等于无限请求、无限重试或并发。

首版不为了优化压缩率耗尽 CPU，不安装新压缩框架。PAR2 块大小/性能要实测，取工具支持的参数范围；不预设“加了 15% 只多花 15% 时间”。

## 7. 夸克交接与回读证明

### 7.1 首版人工传输

项目生成上传清单，列出本批包、恢复文件和控制包及其密文摘要。用户通过官方客户端传到专用位置，记录账号本地别名和远端路径；不要求分享链接。程序不读取夸克 Cookie、密码或浏览器会话。

用户确认上传后只进入 `user_reported_uploaded`。需要从所记录的夸克位置重新下载到不同的回读目录，再选择该目录供核验。不能把原始 staging、原包目录、其链接或改名副本当自动云端证据。

程序能自动证明“所选文件字节与期望一致”，但不能仅凭文件内容证明它真的经过夸克或客户端没有使用缓存。因此首版明确记录：传输来源由用户确认，内容由程序核验，证据为 `user_returned_verified`。同路径、同文件身份、硬链接等明显自验证应拒绝；不能假装已完成服务端独立证明。

未来若接入正式可维护的远端接口，再增加 `adapter_readback_verified`，包括远端对象身份与实际读取结果。仅文件名、大小、时间戳或未知语义 ETag 不算内容核验。rclone 的回读核验方法仅作为参考，**未证明它能直接接入夸克**。[参考机制](https://rclone.org/commands/rclone_checksum/)

### 7.2 回读验收

1. 将回读对象关联到冻结上传清单；同名不作为身份，实际大小与完整 SHA-256 必须匹配。
2. 对每个数据包验证密码、manifest、成员集合和每个成员 SHA-256；多文件不能只测试一个样本。拒绝额外未知成员、重复路径、遍历、链接、超限解压等。
3. 单独核验 PAR2 与控制包；检查恢复组完整、能力不降级。控制包必须能解密和重建目录。
4. 在同一短事务提交本轮观察、核验算法/工具版本、时间、来源等级、计数与失败清单。没有通过的对象不被批次总体“完成”掩盖。
5. 生成只读核验报告和可释放候选；不在这一步执行原件删除。

第一次验收每个对象完整读取；以后可按时间分批复核，过期仅表示证据陈旧，不自动认定数据已坏，也不自动重新下载。首次核验不能用抽样或云端缩略图替代。

## 8. 空间释放协议

### 8.1 必要条件

可释放清单仅包含：

- 原件已被精确成员清单覆盖，封包/回读解包与摘要均通过。
- 该批所需控制包、恢复对象及目录快照已核验，密码恢复演练已通过。
- 远端位置明确，用户已确认本次人工传输来源；接受当前单站模式。
- 源文件仍是清单中的同一身份和字节，不是后来被编辑的新版本。
- 无相冲突的下载、归档、恢复或文件写入操作；记录与计划版本一致。

不设置“上传后经过几分钟就能删除”的时间捷径。可释放依据有明确 evidence ID，不是一个可任意点亮的成功开关。

### 8.2 执行与恢复

A1—A4 不实现用户原件删除，只输出清单。A5 在验收后提供显式“释放这一批本地空间”，显示准确数量、字节与归档去向；只执行此次用户选定的范围。

逐文件在账本写 `release_prepared`，重新检查绝对路径归属、重解析边界、文件身份和内容；通过可验证的 Windows 文件句柄/独占访问策略防止检查后被替换。不能可靠保证身份时标冲突并跳过，禁止仅凭名字删除。

删除结果再提交 `released`。若中途退出，恢复逐项核对：文件还在且身份相同可继续；已不存在且有匹配 prepared 及充分归档证据时完成对账；出现新文件或不确定时保留待确认。不能靠整目录递归删除减少代码量。

放入回收站通常还占本地空间，不能显示为已真正释放。若提供永久释放，产品文案必须准确、执行范围具体；当前设计授权不等于已授权现在删除图库。归档后的恢复依赖云端访问与密钥，不能把它描述为删除的无条件本地回滚。

用户自行在资源管理器删除时，无 `release_prepared` 就不能伪造一次程序执行。若已有核验归档，可记录后续观察为“本地不存在，有已核验归档”；若只有用户历史转存陈述，则维持未核验等级。

## 9. 持久化与模块边界

### 9.1 单库与可重建导出

继续由 `download_logs/library.sqlite3` 的唯一写入者维护业务事实，逻辑新增如下表组，不启动第二个生产数据库服务。A1 已有[临时副本 v1→v2 基础](A1_FOUNDATION.md)，包含内容/路径、实际对象、观察与位置关联；它尚未接入唯一写入者，不允许直接迁移生产库。已有 schema_version=1 不能原地增加表而不升级版本。

| 逻辑表/实体 | 关键字段与不变量 |
| --- | --- |
| archive_batches | batch_id、方案版本、不可变范围、容量计划、阶段与暂停原因 |
| archive_assets | asset_id、可选 artifact_id、来源等级、size/hash、PathRef、文件代次；原始来源事实不覆盖 |
| archive_packages / members | package_id、密文 hash/size、格式/工具/key_ref；成员相对路径唯一，封存后不可改写 |
| archive_groups / objects | 组、数据/恢复/控制对象、编码参数、目标与实测能力；完整组不能缺必需对象 |
| archive_locations | 对象、远端别名/路径、locator revision；地址变更不改变密文身份 |
| archive_checks | 对象、观察与内容摘要、来源证明等级、工具/策略、时间、结果；追加记录 |
| archive_releases | 精确本地对象、计划/命令 ID、归档证据、prepared/结果；幂等且不覆盖未知文件 |

可共用既有 events，批次事实与 GUI 快照一起确认；hash/网络/工具进程不占 SQLite 写事务。历史下载表不因归档删行，旧导出名单仍可使用。核验结果关联精确包代次、根/远端映射 revision；迟到事件不得覆盖新状态。

归档目录和 manifest 是可携带快照与恢复材料，不是第二套同时写入的完成账本。数据库丢失可以从解密清单重建“内容与位置”，随后做新的当前核验；不能据导出快照臆造原来没有的删除或远端访问事件。

## 10. 恢复、巡检与旧图库接纳

恢复以作品/画师或包 ID 定位 → 选择新目标目录 → 获取最小所需包 → 校验密文 → 必要时同组纠错 → 解密到隔离目录 → 逐成员核验 → 无覆盖发布。默认不恢复整个 500 GB。缺包修复可能需要同组其他包和恢复对象，UI 要显示额外下载量与空间。

首轮真实样本全程保留源文件；只有演练成功才允许下一阶段。长期存储不是一次验证后永久免检；可按上次检查时间生成轮换复核清单，首版人工触发，无系统定时任务或隐式联网。

旧图库分三类：有原始摘要且仍有原图、只有本地文件、仅在云端且无原始摘要。分别继承原证据、建立当前基线、按选定小批取回后建基线；不能统一标“原图已证明无误”。旧云端原件/旧压缩包在新归档未完成前不删除，也不因新包已上传而自动清除旧云端副本。

## 11. 发布与未决项

安装/共享依赖维护、schema 迁移、真实上传、原件释放分别作为独立实施动作留证据。安全密码通道、Windows 工具来源、实际夸克客户端回读过程、PAR2 参数与资源、准确磁盘余量均尚未验证，不写成现成能力。

保留当前启动与界面，先在离线小样通过，再接入一个轻量归档页面/工具入口。原图下载质量与性能不因增加归档而下降；无缩略图、相对路径、少依赖要求继续有效。
