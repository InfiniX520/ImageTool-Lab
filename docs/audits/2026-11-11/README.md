# JpgPng、gallery-dl、PixivUtil2 技术审计与选型对比

审计日期：2026-11-11。对象为当前本地 JpgPng，以及已下载、固定提交的 gallery-dl 和 PixivUtil2。本文是源码、依赖和受控离线行为审计，未进行三者的同条件真实账号下载或速度排名。

## 1. 结论

三个项目均有可用的工程成果，也都有边界。现有证据不支持“自研必然最好”，也不支持“开源项目成熟，所以可以直接替换且保证质量”。

- **通用下载引擎、成熟 CLI、批量输入、可组合过滤、多站点支持：gallery-dl 优势明确。** 它是优先评估的通用执行层，但默认原图失败后可降级到较小图；续传范围检查、文件发布结果和归档记录也有本轮复现的问题。严格收藏需要调整默认策略并补充验证。
- **Pixiv 专用归档功能、传统数据库维护、作品信息及动图相关选项：PixivUtil2 很丰富。** 它并非只有命令行，快照中已有 Tk GUI；其缺失文件清理机制在部分路径比 JpgPng 的当前收据复用更实际。但图像校验默认关闭、旧文件判断较宽松，OAuth 响应进入调试日志的问题应先处理。
- **按用户习惯渐进补画师历史、页级账本、严格交付、无预览桌面操作及受控关注整理：JpgPng 有明确的定制价值。** 这些价值不能掩盖它的缺点：已完成收据复用不重新核验磁盘文件，本轮已复现删图和同尺寸替换后仍被复用；类型覆盖较窄，接口维护、依赖复现和浏览器自动化也有成本。

对当前用户，建议保留现有业务数据和启动方式，先解决 JpgPng 的收据有效性及共用依赖风险，再以固定稳定版 gallery-dl 做严格配置下的有界真实对照。若对照通过，优先复用成熟引擎中确实能降低维护成本的部分；界面、任务账本、核验和关注整理按实际价值保留。**本轮没有实施迁移，也没有修改生产源码或升级共用环境。**

详细问题及复现条件见 [FINDINGS.md](FINDINGS.md)；版本、检索覆盖、测试限制和复核方法见 [VALIDATION.md](VALIDATION.md)。

## 2. 基线、范围与证据强度

| 项目 | 本轮基线 | 完整性与覆盖 |
| --- | --- | --- |
| JpgPng | 当前本地工作树；不是干净的上游发布包 | 178 个声明范围内的源码、测试、入口及根说明文件建立 SHA-256 基线；其中 163 个 Python 文件进行 AST 检查。保留原有未提交修改 |
| gallery-dl | 官方 Codeberg 提交 `789a5085d900042090a197e8c40e5b94533f877a`，2026-11-10；源码版本 **1.33.0-dev** | 833 个文件逐一匹配已核验快照；796 个 Python 文件进行 AST 检查 |
| PixivUtil2 | 官方 GitHub 提交 `46bb910cd60c213c9199d939859670a044450239`，2026-10-25 | 152 个文件逐一匹配已核验快照；40 个 Python 文件进行 AST 检查 |

gallery-dl 的开发快照不等于稳定版。本次动态探针针对该开发快照；此前另取 v1.32.19 的五个核心文件，确认其默认 fallback 等关键事实。**本报告未把开发快照的全部复现结果扩大为 v1.32.19 的完整动态结论。** PixivUtil2 的 pyproject 版本 `0.1.0` 也不足以标识这次源码，采用完整提交号。

证据按以下强度表述：

| 标记 | 意义 | 不能据此推断 |
| --- | --- | --- |
| 静态确认 | 固定源码中可定位的分支、配置默认值或数据结构 | 所有真实环境均触发，或外部接口当前一定可用 |
| 受控复现 | 合成响应、临时目录、测试数据库中实际执行相关代码 | 已在真实账号大批量触发，或已完成全流程联测 |
| 依赖公告匹配 | 指定版本落入维护者/OSV 受影响范围 | 已被利用、当前路径必然可达，或机器已受感染 |
| 历史验收 | 以前批次留存的测试与真实小样记录 | 本轮重新验证，或能够代替三项目同条件比较 |
| 未验证 | 本轮没有足够证据 | 不存在、不能用，或一定有缺陷 |

全量文件清点和声明范围内的风险模式搜索已经完成；人工深入审查集中在 Pixiv 适配及共用下载、鉴权、路径、记录、恢复、日志和扩展执行层。gallery-dl 的其他站点适配器纳入扫描，**没有逐行人工审完所有站点，也没有运行所有站点功能**。业务资料、真实凭据和下载库没有作为测试输入。

### 3.2 质量、续传与记录

| 维度 | JpgPng 当前主线 | gallery-dl 本快照 | PixivUtil2 本快照 |
| --- | --- | --- | --- |
| 静态图首选来源 | 元数据的原图字段；拒绝预览替代 | 原图字段 | 默认 `downloadResized=False`，使用原图路径 |
| 原图失败后的默认策略 | 明确失败/待处理 | **fallback 默认开启，可尝试 master1200 等较小图** | 不把选用缩小图作为默认；本轮未覆盖所有失败回退路径 |
| 静态图字节保持 | 正常交付不转码 | 正常默认下载不转码；后处理另计 | 普通下载不转码；XMP/转换等可选动作另计 |
| 文件长度 | 检查长度、范围和实际交付状态 | 拒绝已声明长度的短响应 | 底层也会拒绝已知长度的短响应，不能说完全不检查 |
| 未知长度伪图 | 无效 PNG 探针被拒绝 | 签名像 PNG、内部损坏的样本被接受；HTML 对照被拒绝 | 底层可发布未知长度非图样本；默认 `verifyImage=False` |
| 图像可解码性 | PNG 深检查；JPEG/GIF/WebP 主要是结构检查，未完整像素解码 | 默认签名/类型等检查，非完整图像解码 | 可选 Pillow 加载，但允许截断图；没有严格拒绝所有截断的保证 |
| 单文件部分续传 | 有自有检查点、Range/强 ETag、前缀摘要与恢复约束 | 有 `.part` 与 Range；已复现响应起点不符仍接受，未发送 If-Range | 有 `.pixiv` 临时文件；本轮未确认同等级字节级跨进程 Range/ETag 协议 |
| 最终文件与记录顺序 | prepared、发布、完成分步并可恢复 | 发布后 archive；已复现 `finalize=False` 未阻止登记成功 | 临时文件发布、页/作品数据库记录；未证明与 JpgPng 等价的跨步骤恢复协议 |
| 历史去重 | 页收据、品质、输出位置等条件 | SQLite archive + 本地文件存在判断 | SQLite 页/作品记录、大小/时间等判断 |
| 删掉已下载文件后 | **当前可继续信任旧收据** | archive 命中可直接跳过，无磁盘复查 | 部分作品流程会先清理缺失文件记录，这是实质优点 |
| 同尺寸替换后 | **本轮复现仍复用旧收据** | archive/存在判断不等于摘要复核 | 同大小/同时间等条件可能跳过，非内容完整性判断 |
| SHA-256 的作用 | 交付证据及恢复中有实际使用；跨任务复用尚缺磁盘复核 | 可配置 hash 后处理；默认 archive 不是摘要库 | 没有确认默认等价的持久页摘要复核流程 |
| 作品级完整性 | 选定页完成后才计作品完成；类型/筛选范围仍须说明 | 按文件处理；需额外定义作品级完整和任务账本 | 多页和数据库已实现；本轮未验证全部异常分页/转换组合 |

原图质量应依次问：URL 是否是期望来源；实际收到的字节是否完整；图片结构是否可接受；全部选定页是否保存；之后文件改变是否会被发现。三者都没有从平台取得每件作品的独立可信摘要来证明“绝对等于作者上传源文件”。本地 SHA-256 证明收到什么、以后是否改变，不能单独证明远端就是最高质量源。

动图需要另外审查帧来源、分辨率、时序、帧数和封装。gallery-dl 默认 Ugoira ZIP 路径与 `ugoira: original` 独立帧路径不同；“ZIP 无损”不自动说明帧为最高质量。PixivUtil2 的可选转换不能与原 ZIP 字节保持混为一谈。JpgPng 未实现相应能力，更不能靠不支持来取得“动图质量更高”的评价。

## 4. 性能判断：能确认什么

三者均有流式写文件的实现，不存在“某一款必然把所有原图放进内存”的结论。gallery-dl 默认 HTTP 块约 32 KiB，PixivUtil2 默认下载缓冲约 512 KiB，JpgPng 交付使用约 64 KiB 块；**块大小不能直接排出速度或内存名次**。

| 成本来源 | 观察 | 对当前用户的意义 |
| --- | --- | --- |
| 网络与请求数量 | 详情补齐、网页补漏、HEAD、重试、动画独立帧、作品数量均影响总时间 | 比较时须统计实际请求，不能只用“下载几百张”作单位 |
| 本地验证 | JpgPng 做结构/摘要/持久化；PixivUtil2 可选 Pillow；gallery-dl 默认较轻 | 更严格的本地证据有 CPU/I/O 成本；是否值得按质量要求决定 |
| 数据库 | 三者均使用 SQLite，但数据语义和写入频率不同 | archive 更轻不代表任务管理更好；复杂账本也不是免费收益 |
| 并行与 UI | JpgPng 将网络/文件/SQLite 与 Tk 事件处理分工，并限制队列 | 历史长测有价值，但不是三项目吞吐量基准 |
| 日志 | JpgPng 当前日志有有界队列和脱敏；PixivUtil2 有轮转；gallery-dl 有可配置输出 | 不能把“存在日志系统”当成已证明零卡顿或零敏感泄漏 |
| 看图整理 | 只有实际分类时需要多幅样图，和下载主界面的无预览设计不冲突 | 不应为了整理功能给所有下载任务增加缩略图请求 |

本轮没有在同一节点、同一作品清单、同一请求间隔和缓存状态下测时长、峰值内存或 CPU。因此没有给出速度倍数、资源排名和“最稳”的统计结论。22 个探针耗时和项目测试耗时反映测试样本，不代表下载性能。

## 5. 安全和数据可靠性摘要

| 编号 | 对象 | 重要发现 | 证据与边界 |
| --- | --- | --- | --- |
| D-01 | 当前共用环境 | urllib3 2.7.0 匹配三项安全公告，certifi 2026.7.22 匹配根证书移除公告 | 版本和公告范围已核对；利用条件需分别判断；不是已受攻击证据 |
| D-02 | PixivUtil2 uv.lock | curl-cffi 0.13.0 匹配重定向 SSRF 公告 | 未安装该锁文件；源码中的 curl 调用涉及 FANBOX，不能直接等同 Pixiv 图片下载必然可利用 |
| J-01 | JpgPng | 删除或同尺寸替换已交付文件后，新任务仍可复用旧收据 | 真实临时数据库与交付器受控复现；影响长期库完整性 |
| G-01 | gallery-dl | 默认 fallback 可降级成功 | 源码与候选 URL 探针；可以关闭，不是无法下载原图 |
| G-02 | gallery-dl | 206 起点不符仍拼接，未绑定 If-Range | 受控响应复现；异常服务器/源变化场景 |
| G-03 | gallery-dl | 自定义远端独占目录段 `..` 可越出输出根 | 仅路径计算复现，未越界写盘；默认 Pixiv 的 ID 前缀模板不同 |
| G-04 | gallery-dl | 临时文件消失、finalize 返回 False 后仍可写成功 archive | 受控发布失败复现；罕见竞争条件也应准确报错 |
| G-05 | gallery-dl | 不前进的分页可重复；逻辑 rate limit 循环不受普通 HTTP 重试数限制 | 合成分页及停止哨兵探针；没做无限真实请求 |
| P-01 | PixivUtil2 | OAuth 成功响应含令牌字段，原样进入 debug logger | AST 隔离方法复现；默认 DEBUG 且日志启用，无真实令牌参与 |
| P-02 | PixivUtil2 | 默认图片核验及旧文件判断不足以证明完整 | 静态与底层探针；已知长度短响应拒绝也得到确认 |
| P-03 | PixivUtil2 | 自定义清理配置使用 eval | 本地可信配置可执行代码；不是远端默认 RCE |

安全评价同时考虑默认值、可达性、授权和影响。不把用户主动配置的命令后处理与隐蔽恶意执行混为一谈；不把无签名旧 DLL 直接判为恶意文件；不把某个依赖的 CVE 嫁接到没有相同组件的项目。

维护者对 urllib3 的 [分块头内存问题](https://github.com/urllib3/urllib3/security/advisories/GHSA-vxq7-64xx-v4gw)、[Deflate 循环问题](https://github.com/urllib3/urllib3/security/advisories/GHSA-gh4c-6fx4-qh6g)、[HTTPS 代理 TLS 问题](https://github.com/urllib3/urllib3/security/advisories/GHSA-8988-9cw3-xx77)，以及 certifi 的 [emSign 根证书公告](https://github.com/certifi/python-certifi/security/advisories/GHSA-6q48-6c7w-9gw2)均有原始说明。受影响的共用环境关系到 JpgPng；如果 gallery-dl 复用同一环境，也承担相应依赖风险。不能因此把它们记成“只有上游有问题”。

## 6. 本轮验证结果

| 验证组 | 实际结果 | 解释 |
| --- | --- | --- |
| 三项目声明范围内 Python AST | 无语法错误 | 不代表功能正确或安全 |
| JpgPng 相关离线回归 | **208 passed，3 deselected** | 覆盖图片校验、规划、筛选、交付、记录、关注、整理；3 个实际子进程用例不纳入本轮守卫执行 |
| gallery-dl 上游选定测试 | **112 passed，8 failed** | 8 项均是 Windows `\\` 与硬编码 POSIX `/` 的期望差异；保留原始失败，没有改测试消除失败 |
| 跨项目独立行为探针 | **22 个断言符合预期** | 包含正常对照与“确认缺陷存在”的断言，不能写成“22 项质量验收全通过” |
| PixivUtil2 完整应用/GUI 测试 | 未执行 | 当前缺依赖，未安装；只执行已审阅的 AST 隔离函数/方法，不能等同全应用 |
| 依赖公开公告查询 | 52 条查询，覆盖 50 个不同包版本组合 | 初始 39 条，另从当前运行依赖闭包补查 13 条；锁文件和本机共有项另去重；公告别名去重后为 5 个 GHSA |
| 官方快照完整性 | 985 个上游文件与已核验摘要一致 | 来源完整性不是安全认证 |

受控执行在独立源码副本中完成，使用 Python 审计钩子限制外网、子进程和批次外写入，允许上游测试所需本机回环。它是应用级防误操作措施，**不是操作系统沙箱**。所有真实账号接口请求为零；公开文档、源码元数据及漏洞库联网查询不使用账号凭据。

此前 JpgPng 的 906 项验收、两小时离线长测及真实小样，属于历史证据；关注整理 CLI 的 89 项相关测试和网站补偿核对也属于历史交付。不能与本轮数量相加后宣布比上游更可靠。

## 7. 选型与后续工作建议

### 7.1 按任务选择

| 要解决的问题 | 建议 | 前提 |
| --- | --- | --- |
| 尽快获得成熟的批量 CLI、多站点、丰富命名过滤 | 优先验证 gallery-dl | 固定稳定版、明确配置、独立输出和严格文件核验 |
| 深度使用 Pixiv/FANBOX 传统归档、数据库管理和动图选项 | PixivUtil2 值得保留为候选 | 先处理日志敏感信息、锁文件和校验策略，并做完整应用小样 |
| 保留已经认可的桌面体验、渐进历史补全及可解释结果 | 继续使用/修补 JpgPng 相应模块 | 首先修复磁盘收据复查缺口；不要宣称未支持类型已完整收藏 |
| AI 多图判断后整理真实关注分组 | 现有 organizer 工具可以继续推进 | 工具已发布不等于分类完成；浏览器稳定性、E1-3/4 仍需验收 |

### 7.2 建议的处理顺序

1. **共用依赖维护**：单独形成可回滚的环境变更，核对 urllib3、certifi 修复版本及工作区其他项目兼容性；本次审计不直接更新。
2. **库完整性闭环**：JpgPng 复用收据前按策略检查存在、大小、摘要，区分未核验、失效、待修复。文件检查应在 I/O 所有者中进行，避免放进 SQLite 事务或 Tk 回调；不能简单加一个耗时全库扫描。
3. **同条件真实小样**：固定少量公开可访问静态作品、至少两个多页作品；动画若纳入，单独验收。隔离下载、固定配置，核对作品/页/字节/摘要、请求和错误，不触碰原库和账号分组。
4. **迁移边界验证**：若采用 gallery-dl，先关闭 fallback，明确断点策略、进程停止、日志脱敏、ID archive 与本项目收据的转换；Range/发布问题未解决前，不直接用 CLI 退出码冒充严格交付证据。
5. **减掉重复维护**：实际对照证明成熟适配器能完成需求后，减少重复抓取代码。跨进程调用、直接引入和复制源码各有维护/许可边界，应另做具体设计，不能仅凭一句“接个 CLI”推导出低成本。

### 7.3 本轮不做的结论

没有速度排行榜、封号概率、账号绝对安全保证或“百分之百万无一失”承诺；没有因为已有投入而保住全部自研，也没有因为明星项目而忽略默认策略和故障路径。最终是否替换执行层，应以用户需求下的质量证据和维护收益决定。
