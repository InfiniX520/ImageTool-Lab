# 下一轮开发指导：先收住清理权限和错误协议

基线产品 `9ee6206`；以包含本审计的独立分支为接续点。日常 `4ba891e` 不代表这些修复已部署。开始前检查实际 HEAD、dirty 状态、最新审计、被审 10 文件的差异与适用 AGENTS。不要沿用“全部关闭，可以替换”的旧结论。

## 0. 本轮目标与不变量

目标是关闭 [FINDINGS](FINDINGS.md) 中 6 类缺口，独立推进 Tk 根因诊断；暂不追加归档产品功能。继续优先保证原字节和数据安全，其次性能、最后界面细节。不改已认可视觉风格，不加缩略图、不另建 Node 环境，不进行真实恢复或清理来证明合成修复。

必须共同遵守：

1. 看见文件不代表拥有它。清理权限来源于本操作创建记录和仍匹配的身份，不来源于目录名字、时间、扩展名或路径前缀。
2. 无法观察不同于已观察到不符，更不同于通过。CLI 类型和退出码必须一致。
3. 返回游标不等于已证明扫描前缀。当前没有证明链，保持 `complete_prefix=False`。
4. 刷新必须建立新读取代次；丢弃旧展示回调不等于回滚已提交的写任务。
5. 文件句柄身份、路径绑定、内容摘要分开表达；未知不能靠另一项正常信息补成“已证明”。

## S0：主执行者先冻结契约和验收

先只读对齐 `_discard` 三个调用点、`backup_library` 全生命周期、`restore_check/main`、scan `_resume`、控制器 watcher 和归档 `file_record`。用 GitNexus impact 确认拟改符号的所有调用者；尤其不要漏掉失败备份路径和 SQLite 自动生成的 sidecar。

在现有 AMD1 之后新增小幅契约修订或清楚的增补，不改旧审计原文，明确：

| 议题 | 需要冻结的输出/责任 |
| --- | --- |
| 临时成员所有权 | 操作 token/目录身份、成员创建身份、允许处理的种类、目录替换与身份未知时的保留策略 |
| 清理结果 | 主操作状态与 cleanup 状态独立；残留位置/原因可诊断；成功不掩盖清理故障 |
| 备份异常 | 创建目标后直到 manifest 原子完成的统一边界；主错误、cleanup 次错误、中断分别保留 |
| restore-check | 健康、兼容、组一致、无法观察分别是什么；组合到 JSON state 和退出码的判定表 |
| 临时目录位置 | 同级/系统临时回退的顺序、上限、失败分类、强杀残留；文档与实现一致 |
| UI 查询 | 独立 query generation 的创建、失效、成功/错误回调门禁；与批次 epoch、恢复任务的关系 |
| 归档证据 | 句柄身份与路径绑定的 unknown/changed 优先级；不得改变历史证明的含义 |

把 14 个独立用例作为红基线接入：最终证据应为 12 红/2 绿。PA-03 属仓库外脚本，按摘要取冻结副本；不得导入旧 `apply()` 去搬动历史目录。测试可迁到正式 tests，但原审计证据保持只读；需要适配注入点时逐条说明等价时序，禁止降低断言或添 xfail。

在新增反例之外，按以下各节补邻接矩阵。现有测试只是必要下限，不能把“14/14 绿”当成全部设计已闭环。

## S1：单一所有者串行修改维护生命周期（最高优先级）

所属文件：`core/library_maintenance.py`，以及必要的新小型所有权模块。该文件的 cleanup、backup、verify、restore-check、CLI 错误映射属于同一错误/资源边界，**不得拆给三个智能体并行改同一文件**。

### S1.1 清理 CL-01

建议先设计再替换 `_discard`，而不是在旧递归函数中继续堆条件。

- 在创建目录及成员时记录身份；所有权记录不能事后把目录里当前所有项“收编”成自有。
- 普通文件也要证明仍为原成员；名字相同但对象替换不能删除。目录已替换、身份未知、访问拒绝、出现陌生项均保留并报告。
- Windows junction、symlink、其他重解析点不遍历。不能认为 `is_dir(follow_symlinks=False)` 已涵盖所有类型；不能先 resolve 到目标再把目标当允许删除的目录。
- 删除前复核父目录与成员身份；明确检查/使用之间仍可能出现的竞争。若平台能力不能给出所需保证，采取非破坏保留，避免以“存在概率低”跳过。
- SQLite 创建的 WAL/SHM/journal 也必须说明由谁创建、何时登记；不得为了清空暂存目录按后缀通杀。无法区分时保留并输出残留事实。
- 清理没有权限时允许留下自有残留，不能递归扩大范围。主核验结论与 cleanup 结果分别展示；未知成员保留时 cleanup 不得写成全部清理成功。

验收至少包括：正常只删自有文件；陌生普通文件；陌生子目录；junction 指向另一合成目录；自有同名替换；目录根替换；成员/父目录不可读；清理中失败；合法 sidecar；新建失败；备份失败和 verify finally 两类调用。对每类危险注入先断言合成两端绝对路径位于本批根内，记录哨兵前后字节/摘要，不对用户资料试验。

### S1.2 失败协议 WR-04

从 `target.mkdir` 成功后直到最终 manifest 完成，为所有后续阶段建立同一资源/失败边界：复制、fsync、源组复核、counts/definitions、copy inspect、逻辑指纹、manifest 序列化/写临时文件/flush/replace。

主错误必须先被保存，再尝试安全清理。清理失败附加为诊断，不能覆盖主错误；`KeyboardInterrupt`/`SystemExit` 不改成普通 BackupError。不是所有错误都必须删除残留，关键是**失败明确、所有权保守、留下什么可查**。不要用 `except BaseException: return {ok: False}` 吞掉控制流。

输入阶段在路径操作前拒绝 NUL、无效成员/模式/尺寸；已能观察的类型错误采用统一 typed 拒绝。暂存区不可建立属于执行/观察条件不足（契约退出 3），不是内容损坏（2）。确保 JSON 模式不打印 traceback 或混入多段非 JSON 文本；文本模式也给出主因和残留。

验收逐阶段故障注入；至少实际触发最后写清单、复制失败+清理失败双故障、NUL 成员、暂存区不可用。每个 hook 要记录“确已执行”，排除因前置验证先失败而产生假绿。补同名目标再次尝试时的明确拒绝，不能自动接纳未完成备份。

### S1.3 restore-check CL-02

先写判定表再改 CLI。`status != compatible` 不应仅因不存在 orphan WAL 就 `state=ok`。损坏、空白、不兼容、missing、inspect 异常分别可解释；WAL 无权限/类型异常不当 0 字节。当前 header 检查能证明的范围必须明确，不能声称证明了任意 WAL 的来源。

覆盖 online snapshot / 匹配 file-group 正常组、损坏/空库/错 schema、非 WAL 库旁有 WAL、WAL 无法 stat/read、主库组成员替换、健康库但未知组来源。恢复 runbook 继续先验证备份、保全旧组、失败整组退回；不得为加快演练跳过保全，不新增自动覆盖真实库功能。

S1 整体完成后跑维护/备份 generation/restore protocol/独立反例相关集合，再合并到集成分支。前后操作事实与资源所有权必须由同一审查者整链复核。

## S2：scan 只修证明口径（CL-03）

所属 `core/library_scan.py`，不碰 S1 的 CLI 同一文件，新增回归放自己的测试模块。当前最小而正确的改变是无前缀链时恒 False；返回 next_cursor 只给“可以从哪继续”的提示。

矩阵：完整 full_walk、max_files 中断、max_bytes 中断、大文件跳过预算、开始即 cancel、中途 cancel、页间错误、裸 continuation 已到 EOF、显式单页、跨页首坏末绿。维持当前已修的严重度单调与退出 5；不得退回按最后一页重新判定整体。

不在本轮新增迁移、持久 resume、全局索引或缓存。未来可验证链作为独立设计，避免为了消除一个布尔值缺陷引入更大系统。

## S3：核验面板刷新代次（WR-06）

所属 `gui/collection_controller.py` 和核验控制器测试。不重做风格、不加加载预览、不把恢复写任务放主线程。

进入新作业/批次、点击刷新、重新打开同一页或回到同一 cursor 都需明确查询代次。刷新应立即清空可操作选择、置 loading、解除旧 summary/pages 的观察、发新请求。生产者仍在执行时可继续完成，但旧成功和旧失败都不能写入新代次视图。不要仅靠 `(batch, cursor)`，它们可能重复。

分别管理查询代次与已提交恢复任务。刷新不撤销已执行写命令，也不能因 epoch 变化丢掉其持久回执；可提示刷新后查看新事实。不要盲目 Future.cancel：先确认生产者对 cancelled Future 的 set_result/set_exception 行为，否则可能把界面修复变成后台线程异常。

验收：旧响应在刷新后才返回；旧错误在新成功后才返回；连点刷新；第一页→下一页→第一页；切作业后旧响应；退出面板后返回；正在恢复时刷新；新查询出错再重试。断言请求数/代次、显示行、按钮启用状态和最后可见错误，而不只断言内部字段被赋值。

保留 expected_delivery_id 后端前置比对、分页上限和 read_revision 不保证同快照的提示。

## S4：归档身份能力与可追踪源码（PA-03）

该工具不在产品 Git 中。先取本审计固定摘要快照，另立清晰版本化的维护工具位置；保留旧历史脚本和批次记录，不覆盖已完成批次来制造“修复前也正确”的印象。推荐单独 `tools/maintenance/` 子目录（或既有维护仓库），由主执行者确认与工作区规则兼容后落位，不给产品启动路径增加依赖。

区分 `handle_identity`、`path_binding`、`content`：句柄前后有效且一致，最终路径身份未知时，路径绑定必须 unknown；已知句柄发生变化时，即使路径未知也应 changed。将各分量状态显式归并，避免 None 同时表示“匹配”和“无证据”。

验收包含：全有效、句柄全 0、仅第一次 fstat 未知、仅第二次未知、仅最终 lstat 未知、路径身份与句柄冲突、已知句柄变化+路径未知、重解析点前后出现、同内容同长度替换、跨卷身份合理改变。跨卷当前没有真实环境时明确未测，不伪造实机通过；合成只能验证状态分类。

旧 18 批摘要证明和缺失的前身份仍分开保留。不能把修好采集器等同于恢复历史身份。真实 apply 后续另批、先只读计划与路径校验，再按授权和证据门槛处理。

## S5：Tk 稳定性单独诊断

不要借本轮审计把“gc.collect 后通过一次”提升为根因修复，也不因基线失败就直接重装环境。

固定 Python/Tcl/Tk 路径、环境变量、-s 捕获模式和用例顺序。分别记录单根/多根、dispose 次序、after 回调、Tk Variable/Image 存活和释放线程，区分 Tcl 初始化异常与原生崩溃。基线与候选使用相同进程组织；连续重复的次数和中途失败原样记录，不只保留最后一次通过。

可以先保持已有逐条隔离验证用于其他修复收口，但未解决根因时“持续桌面运行稳定”仍未证明。若与 S3 的 controller/view 触及同一生命周期，S3 合并后再做，禁止并行改同一销毁路径。

## 组织、并行和合并

主执行者先结束契约对齐这一轮；用户确认后，按工作区 AGENTS 用继承上下文的 fork。没有合适工具或未获确认时由主执行者顺序推进，不用空白低上下文智能体补位。所有派发沿用工作区要求的质量提示与相同推理能力。

| 工作包 | 可独立范围 | 合并约束 |
| --- | --- | --- |
| S1 | 维护 CLI 全生命周期及专属测试 | 单 owner；最高优先级，不能拆文件并行 |
| S2 | library_scan 与专属测试 | 不改 S1 CLI；合并后再测出口协议 |
| S3 | controller 与专属测试 | 不并行开展同文件 Tk 析构修改 |
| S4 | 版本化归档工具及专属测试 | 无产品依赖；不执行真实归档 |
| 集成者 | 契约、日志、总矩阵、索引、S5 | 只有集成者更新共享 TASK/LOG/IMPLEMENTATION |

并行槽不足就排队，不要为了“三并发”创建重复集成者。各 lane 独立 worktree 和测试输出；禁止共用 basetemp、覆盖另一 lane 日志或同时修改共享协议。建议先 S1，再集成 S2/S3/S4；每次合并后针对交叉边界复核，不只拼绿色报告。

保留已有 scratch 原位，登记 3 个 dirty 树的文件清单和摘要，确认不再需要且建立可恢复保全后才另批归档。新批次根从创建时就有 README：基线、分支、真实运行目录、文件所有权、证据位置、当前状态。不要继续往项目根散落脚本。

## 最终验收与允许宣称的结果

1. 每项修复给出触发→行为→结果，反例从真实红转绿；新边界按矩阵覆盖。编译/类型检查采用项目现有能力，不安装工具凑检查项。
2. 全量口径固定为主体排除 3 文件 + view 25 + presentation 9；新增数量另记，核验面板已在主体不重复计。Tk 同进程稳定性与隔离进程通过分别报告。
3. 主执行者完成全量后，再按 AGENTS 使用只读上下文 fork 审最终 diff；问题退回原开发上下文修复。审查关注所有权与错误路径，不以“测试很多”代替阅读。
4. `detect_changes(staged)` 和 `detect_changes(compare, main)` 都跑；前者是本轮真实改动，后者含长期开发累计变化，要分开说明。公开提交只含源码/合成测试/文档，不上传原始运行目录、DB、账号、真实路径配置或日志。
5. 当前导航统一引用最终提交、报告和未关闭项。历史报告不篡改；修复原文件的确切 SHA 与测试运行匹配。提交、推送、标签不得替代真实备份。
6. 6 类缺口与相邻边界通过前，不建议切换日常入口。Tk 根因、真实恢复/迁移、外置卷与真实归档 apply 未验收时仍列明，不能写成“全部完成、万无一失”。下一阶段先有界合成恢复闭环，再在明确授权下准备真实副本演练。
