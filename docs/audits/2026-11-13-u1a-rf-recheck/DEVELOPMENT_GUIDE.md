## 2. 源页观察必须既有界又能推进（S1）

归属：`library_repository.py` 的预检/受理、`observation_snapshot.py`；coordinator/source 的接线等接口冻结后由同一负责人顺序完成。涉及原子受理和 cursor，不让两路同时改这一事务。

先回答：预算是一次观察切片，还是整个来源页硬上限？现有行为把预算当硬失败，用户重试没有新的输入，所以无法推进。建议采用**命令拥有的可续观察状态**，保持原 page 身份和最终 receipt；若改为拆分来源页，需要先完整设计子片/父页的提交、作品预算和重复重放，不能简单切 candidates。

建议最小契约：稳定命令键 `(batch, source/pass/entity, page_identity, page_digest)`；记录未观察队列、已观察候选身份、root revision、policy、checked_at、总资源和有界内存上限。每一片保证至少推进一个合法项目或返回明确不可处理原因；不能无限重读前 32 项。重启可丢弃瞬时观察，但不能伪造已提交；跨重启持久化若需要 DDL，另列迁移门禁。

文件观察始终在写事务外。最终 writer 对完整快照的候选覆盖、代次、根、策略和 freshness 再检查；期间新增 completed 时仅补观察，不把未观察当坏文件。超过单文件上限时有明确的可操作结果，不循环重试同一文件。预算不是豁免质量校验的理由。

必须覆盖：32/33/64 页；20 个多页作品同一来源页；一个文件有多份历史版本；暂停恰在预算边界；排队后取消；重复受理同 page；文件在切片之间被替换；过期观察；只有最终完整原子提交才更新来源 cursor。复用已接受 receipt 仍零额外哈希。

`Future.result(20)` 也要与切片状态对齐：等待超时不能被解释成取消或失败，持有命令/Future 身份查询最终结果。`finish_source` 已知缺口另登记，同一来源 run 不能在 accept 仍进行时先宣称结束。只提高 timeout 不构成协议。

## 3. 发布/取消/清理作为一个工作包（S2）

覆盖 RFA-02/03/06/07。唯一负责人持有 `page_delivery.py`、`delivery_repository.py`、`delivery_cleanup.py`；若修改 library_repository 取消 CAS 原语，与 S1 串行，或 S0 先交付冻结原语后禁止两路写同文件。

先定义事实，而不是写多个散落 exists：

| 观察 | 取消/清理规则 |
| --- | --- |
| 根可用、final 确认不存在、temp 身份完整匹配 | 可取消；后续清理复查实际对象 |
| final 是本交付已发布的对象 | confirm；后来的排除只作用未来工作 |
| 根不可达/权限错误/未绑定 | 保留 prepared/recovery_needed；禁止 already_absent 与取消猜测 |
| 根可用、temp 确定不存在、且交付已 cancelled | 可记录清理终态；这不证明交付成功 |
| temp 被替换/证据冲突 | 保留外来文件，记录诊断和可续待办 |

将取消观察绑定 delivery/batch/state/generation/prepared 摘要/root revision。writer 只验证 expected-old 并写事实，不能在写事务做 hash。需要明示没有跨文件系统与 SQLite 的万能原子事务：物理结果不确定时保持可恢复，不能把不确定性变成 cancelled。

清理事件用一个正式生产者/解析器：写入字段与读者完全一致。旧版本 `outcome=cleaned` 无新布尔字段的记录要兼容读取，不能直接改历史事件；新事实保留 schema、prepared 指纹和结果。测试必须从真实 executor 写事件再查候选，禁止手造一个生产代码永远不会写出的 JSON 来让测试通过。

队列进展：终态记录离队；失败/损坏记录带诊断并允许继续扫描后面的项目；有明确续游标/公平重试规则。测试使用小 limit=1/2，再用 201 条确认默认窗口；混合旧 cleaned、未清理、失败、根离线、坏证据。不要让全表扫描又成为解决小窗口的代价；若需索引/表，独立设计迁移。

取消后的清理不要保留独立直接 unlink 快捷分支。统一持有/核验准确文件对象后删除；至少在任何 DB 往返之后重新核验。严格并发保证若依赖平台文件句柄，应做独立 Windows 实测，无证明时失败保留。禁止删除正式图、扫描目录删 .part 或依据扩展名判断所有权。

恢复异常处理包含补偿自身：区分“别人已完成/已取消/已接管”和“存储不可读”。竞争失败不改 completed、不产生错误的成功/恢复状态；真正 storage fault 交给控制面阻断，不以 catch-all 静默吞掉。加两次 recover_local 交错、主操作异常后补偿 CAS 失败、补偿持久化失败三个测试。

## 4. 统一后继与限制总工作量（S3）

覆盖 RFA-04/05；`delivery_lineage.py` 为唯一解析入口。先固定它与 recovery/carry 的返回协议，再串行接入三个调用点。GitNexus 已发现 `_read_recovery_page`、`_apply_recovery_successor`、`_resolve_carried_successor` 三个直接调用，修改影响 CRITICAL；不能由三路各自实现一套优先级。

遵守精确 handover → 明确可用后继 → 有界取代链的契约；目标匹配要包括页面/路径/质量及所需身份。区分“没有事件”“事件目标坏了”“事件指定的字节需要核验”，损坏不能当作无记录偷偷回退。若决定改变优先级，先改契约并解释现有已记录 handover 如何保持意义。

单次解析用操作内缓存/visited，不能把每个更晚同页行都当树的独立分支无限重复展开。更好的做法是按有界集合读取一次、迭代解析；对总节点、SQL 和结果歧义设预算。memoization 必须考虑剩余跳数/遍历路径，不能把一次因深度不足得出的 None 缓存成全局无后继。不得缓存跨事务的可变结果。

先按新反例验证精确事件优先，再移除事件做 8/16/24/32/64 条历史，加入活动/已完成/坏目标/不同质量；确认相同节点不被重复展开。读前预检和写内 CAS 使用同一解析规则，写内不做文件 I/O；候选在两阶段间变化应返回 typed stale/retry，不偷用旧结果。保持旧批次链接和历史 artifact 不变。
