## 1. 下一批的目标与边界

目标：让“显式选定范围 → 完整消费 → 有界观察 → 确定性清单/容量 → 唯一写入者保存 → 关闭重开重载”在合成目录和临时数据库上成立，拒绝不完整或不一致的输入，并给出明确原因。完成它才可评审生产接线。不是再加按钮、换界面、安装加密工具或立刻处理 500 GB。

开发时保留以下约束：

1. 先读工作区 README/workspace.json/环境说明、项目 AGENTS、本指导及当前 TASK_PLAN。保留已有未提交修改，不 reset、不盲目提交。

3. 使用现有 JuiLiu 解释器、PYTHONNOUSERSITE=1；不为这轮离线修复安装包或新环境。代码和持久化路径用相对路径/显式根映射，不写死 E 盘、个人账号或当前审计目录。
4. 不打开生产库试迁移，不扫描业务目录，不操作 Pixiv/夸克、不下载图库、不上传、不释放文件。用户主动删图不默认补下。

6. 修改函数前按项目规则执行 GitNexus impact，并结合 rg/源码确认调用者。当前 _enqueue 是 HIGH（9 直接调用者、3 流程）；优先修归档适配器对既有队列的使用，不顺带重写生产队列。索引漏掉 writer 草稿，LOW/找不到不能视为零风险。

遇到新失败先保全实际输出并归因，不用旧 TASK_PLAN 历史规则机械回滚用户已有改动。每个工作包有明确结束条件；未达到就记未完成，不把“代码写了”写成已验收。

## 4. R1：先把事实模型修对

### R1.1 内容、路径、批次不是同一主键

建立并写入契约的最小不变量：

- ContentVersion 表达不可变的 asset_id/revision/size/sha256；未知摘要是明确的未知，不能靠观察标签填补历史。
- 一个内容可有多个真实路径，多个批次可引用相同内容/路径。ensure 对完全相同事实返回已有记录；冲突才拒绝。
- 一个当前路径随时间可对应新内容，旧归档仍必须能引用旧代次。将当前路径绑定与历史资产/内容记录分开，绑定更新使用预期旧代次或版本条件，不能覆盖历史内容行。
- 新枚举需要解析既有身份/代次：相同内容重复选取复用，变化的内容走明确新代次，映射不清楚就冲突或待确认。不得对每次扫描都固定 revision=0 后依靠 INSERT 失败解决。

先用 tuple(row) 或明确字段读取消除 Row/tuple 比较差异；再实现“存在→核对→复用，不存在→插入”。只用 INSERT OR IGNORE 会吞掉不一致，REPLACE 可能破坏引用，都不是完整修复。source_kind/artifact_id 是证据，不应为了重载成功改为 user_selected。

释放事件现在只定模型，不实现删除：operation_id 关联一次操作，event_id/序号唯一标识一条追加事实；重复同事件同事实可幂等，不同事实冲突，prepared→released/failed/cancelled 不能抹掉 prepared。A5 再实现执行与故障恢复。

### R1.2 跨表绑定和来源等级

逐项审查所有资产、转存意图、本地检查、归档成员、归档检查、释放引用的完整绑定，不只修探针碰到的一条 SQL：

1. content_key 必须对应同一 asset_id/revision，并且引用事实的 size/hash 与内容记录一致。
2. 已核验、已封存状态必须有该状态要求的非空字段。NULL 安全比较和“该字段必须非空”是两种检查，不能互相替代。
3. archive evidence 的 location/object_revision/package/member/content 必须串起来；不能只证明位置里存在某个同 ID 条目。
4. download_receipt 必须有实际 artifact 引用，并核对它支持的具体内容与质量来源。无历史收据的文件只标 observed_existing/当前基线。
5. 将 LocalObservation 的物理身份、大小/mtime、根版本、run/check、终态与原因、实际读字节等持久化为版本化观察。不得把 cancelled/budget_exhausted 改成 missing/hash_mismatch。

为写入口和重载/维护检查分别测试。单靠 SQL 外键不足以检验摘要/来源等级；单靠 Python 构造器也挡不住旧库或损坏数据。未来释放还必须重新检查当前文件，过去记录不自动授权删除。

实验 schema 改动后保存结构指纹/协议版本和变更说明。旧实验库不能无提示当新结构继续开；可明确拒绝并给重建合成库说明，或实现有测试的副本升级。不要篡改旧检查点、不拿生产数据填测试库。

R1 退出条件：同资产跨批、同内容异路径、同路径新代次、两种 row_factory、NULL 矩阵、合法/无效收据、观察重载、事件追加均有明确成功/拒绝用例；既有 v1 相关契约不变。

## 5. R2：范围资格、身份和完成凭据

### R2.1 同一套资格规则

抽出同一入口供递归发现、显式 files、显式 prefixes 使用。它至少核对根内路径、重解析点、每级祖先排除、敏感文件、实际输出位置、普通文件资格，并产生结构化接受/排除/问题结果。

测试矩阵包括三种入口 × 根级/嵌套 × 默认/自定义输出目录 × 敏感/普通文件；所有入口必须一致。用户自选不默认豁免系统保护。保留排除清单，但报告中不要读取凭据内容。

### R2.2 别拿显示规范化当文件身份

排序键可用确定性文本变换；重复判定必须依据实际身份及可表达的路径等价关系。保留原始路径用于访问和恢复。

在 Windows 上实际创建 NFC/NFD 双文件，验证内容不同的两文件都被保留，或明确报不可表达冲突且不完整；不能只断言返回一个。对正常大小写别名/重复选择仍去重；硬链接单独验证共享内容与路径别名保留。若 PathRef 的通用 target_key 也有碰撞，先限制为明确错误，再单列其影响分析，别扩大成未经审查的全项目路径改写。

### R2.3 完整消费是一个明确产物

建议引入只由聚合/验证入口生成的版本化 ScopeReceipt，实际命名可调整，但字段意义必须保持：

| 字段组 | 必须表达的事实 |
| --- | --- |
| 范围身份 | 请求种类与选择描述、root_id/root_revision、规则摘要、snapshot_id |
| 快照事实 | 选中条目数、排除数、问题数、稳定的候选/路径摘要 |
| 消费事实 | 已消费条目/排除数量、页连续性、无未消费游标、消费集合摘要 |
| 内容对应 | 每个被选中候选有且仅有一个核验结果；路径/身份/根代次能对应回来 |
| 完成状态 | 枚举完整、消费完整、内容就绪各自明确，不能只用一个 full |

聚合器校验同快照、同规则、同根、连续页、不重复不遗漏，并在终页闭合。准备计划再验证库存集合与已消费集合相等；路径和计数相等仍须防条目替换。保存层验证准备产物的版本和绑定，不能只接收任意 scope 字典并信任它。

预算不足时可明确形成一个独立子批次，其范围/未处理剩余必须可解释；不能把整个目录凭据挂在前 200 个文件上。空范围也要区分“确实零候选”“全部被排除”“失败后清空”，不把错误包装成空成功。

祖先链只对身份、类型、重解析点等路径安全事实做相应检查；对选定目录的变化使用范围规则。补“兄弟目录写文件仍可继续”以及“根替换/离线/链接替换必须停止”的成对测试。

R2 退出条件：第一页截断、漏页、重页、换快照、换根/规则、篡改计数/摘要全部被拒绝；合法完整范围和显式子范围可继续；取消、预算、权限失败不产生可封包的完整凭据。

## 6. R3：计划可保存、可重载、可计费

推荐把计划成员放入专用 planned 清单关系，按 batch/序号/逻辑包/资产引用存储；scope_json 只放小型范围凭据和元数据。也可采用有上限且带摘要的分段清单，但须解释为什么比关系表简单。不要把 planned 条目写入代表实际封存证据的 archive_members。

只保留一种权威成员表示，其他摘要/索引可重建并核对。路径、内容和包顺序必须确定；重载按协议版本严格解析，不接受未知字段混入、重复序号、缺段或摘要不符。

把计划入口拆成明确职责（函数名可改，不应为命名而增加层数）：

1. prepare_plan：无数据库写入；验证完整凭据、库存/容量一致、字段/总体边界，返回不可变准备结果和实际负载计费。
2. save_prepared_plan_in_transaction：要求调用者已持有事务；核对已有批次是否同一计划、复用合法资产、写入完整计划，绝不自行 BEGIN/COMMIT/ROLLBACK。
3. save_archive_plan_on_temporary_connection：只有需要保留独立临时连接接口时才存在，由它开启事务后调用第 2 步。与 writer 是两种外层入口，不是两套 SQL 实现。

准备结果必须将每个成员、路径、容量和凭据绑定到同一个规范指纹；指纹用于内容一致性，不冒充来源授权或密码学远端证明。入队负载按完整准备结果计量；若用冻结文件/分段数据作为载体，必须校验其身份/摘要、引用生命周期和取消清理，不能用一个小路径字符串来掩盖无限负载。

入口总预算至少覆盖成员数、计划编码大小、读盘字节、时间、排队字节与输出容量。先做便宜预检，再读摘要，再准备和入队；已达上限时给明确缩批结果。不要等全部图片读完才发现清单无法存储。

R3 退出条件：2,000 条正常合成计划成功完整重载；10,000 条能在既定预算内完成或提前、明确、无副作用地拒绝；边界超限不截断；重复批次同内容成功、不同内容冲突；中途失败无半批计划；旧已封存事实不因重新规划被改写。

## 7. R4：接好唯一写入者，不绕过原队列

在 R1/R3 接口稳定后修 archive_repository：

1. 调用前准备并冻结 payload。不得保留可被调用者改写的 dict/list；返回对象的嵌套可变性也要明确。
2. 用既有队列提交，size_payload/计费覆盖完整命令。不要扩大 _enqueue 限制来掩盖清单表示问题。
3. _dispatch 只开一个事务，调用事务内 SQL 函数；重放是否存在、内容是否一致都在该事务判断，移除队列外 expect_replay 正确性条件。
4. 读连接用明确 close 生命周期；只读方法保持一致快照，避免同一次读取过程中重复全库审计。
5. 关闭、取消、队列满、执行异常均复用原仓库约定；测试不得遗留线程、连接、锁。不要为了修归档读连接顺带重写所有旧仓库方法。

并发测试使用 barrier/event 确定两次调用均在首次提交前到达，不依赖 sleep 碰巧竞争。测试相同计划并发、冲突计划并发、排队后原参数被改写、队列预算耗尽、关闭时仍有命令、事务内部注入故障。

最容易发生的错误是“去掉嵌套事务报错后算完成”。还必须通过 Row、跨批复用、并发重放和嵌套 dict 这些原来被遮住的分支。原暂停逻辑保持，修正错误测试前提。

R4 退出条件：完整 6 项 writer 场景及新增并发/资源用例通过；实际 writer 路径可关闭重开并重载计划；正式启动仍不引用它。

## 8. R5：独立联测，不以单元测试数量代替结果

至少保留以下整链用例，全部走新的范围消费、实际观察、计划准备、writer、数据库重开：

| 场景 | 必须验证 |
| --- | --- |
| 多作品、多页、跨分页、小容量多包 | 原始路径/字节摘要/成员顺序与回读计划逐一一致 |
| 包含敏感文件、输出目录、合法普通文件 | 各选择入口排除一致，普通文件不误排；排除有原因 |
| NFC/NFD 双文件与硬链接别名 | 不丢不同原件，不重复计算物理释放容量，别名可恢复 |
| 观察中改文件、根离线、权限失败、取消、预算到达 | 明确失败/待处理，不产生可封存完整计划 |
| 只交第一页、缺中间页、重复页、换快照 | 拒绝不完整或不一致范围 |
| 两批复用、内容换代、真实 Row 工厂 | 已有事实复用，旧代次保留，不产生假冲突 |
| 保存中失败、关闭重开、同请求重放 | 全事务回滚或完整同一结果，无半批、无重复事实 |
| NULL 摘要、伪来源、关系被篡改 | 写入与重载均拒绝错误事实，未知不升格为已核验 |
| 500/2,000/10,000 条；逐步增加历史批次 | 报告各阶段耗时、比较次数、序列化字节和内存峰值；超限在规定阶段拒绝 |

性能先移除已证实的二次身份比较和 pop(0)，再做基准。不要把大清单基准变成一次读取几十 GiB；合成小文件/元数据足以测计划规模，摘要吞吐另用有界样本。全库完整性审计保留明确入口；常规批次只核对自身和关联事实，不能把审计功能悄悄删掉。

本批每个变更包先运行相关测试；所有代码稳定后再跑一次完整离线回归。环境示例：


## 9. 修复结束回执应当可直接核对
