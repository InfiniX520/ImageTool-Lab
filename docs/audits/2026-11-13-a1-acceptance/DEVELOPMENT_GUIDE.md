## R1：完整绑定令牌、幂等事实与写读不变量（AR4-01/03/06）

主要所有权：`archive_scope` 的绑定/决议契约，`archive_schema` 的接受/绑定/校验，`archive_repository` 对应命令。先写一页决定再改 DDL，责任人保持一致。

### 1. 先区分三个版本

| 版本 | 回答的问题 | 不能代替 |
| --- | --- | --- |
| 内容 revision | 这份逻辑资产的哪一代字节事实 | 哪个物理对象/根映射刚被认可 |
| 绑定 generation / acceptance token | 当前路径状态是哪次成功接受的结果 | 内容摘要或云端回读证明 |
| 操作/观察 ID + 请求指纹 | 这是不是同一请求的重放 | 无条件再次修改当前绑定的权限 |

`ContentBinding.acceptance_id/root_revision` 已存在。优先复用或扩展为不可变 expected 令牌，解决无 acceptance 的旧索引绑定如何表示代次。建议显式区分 `Absent` 与 `Present(content_key, binding_generation, acceptance_id, root_revision)`，不要用 None 同时表达“没有绑定”和“不检查”。

### 2. 写入次序要具体

1. 在受控 writer 的事务中载入当前绑定；低层接口事务归属统一并写清楚。现在 `_require_write_transaction` 在 managed isolation 下会补 BEGIN，文档不能同时声称它从不 BEGIN。
2. 对输入进行完整事实校验：candidate、原始 observation、解析结果、root、path、size/hash/identity、run/check 的对应关系。不修改原始证据来让它“对得上”。
3. 根据 operation/check ID 查历史请求。如果已处理，**先验证请求事实相同**，再返回首次结果；不使用此次 `bound_at` 重造历史接受事件。事实不同立即结构化冲突。
4. 对新请求比较解析时冻结的完整 expected 令牌。当前内容相同但接受事件不同仍属并发变化；保守要求重观察/重新解析即可，不自动解释为安全。
5. 校验替换确认究竟针对哪一个旧接受、新候选和根版本。可保留内部 bool 作纯函数参数，但对未来应用接口不能把无绑定的全局 True 当永久授权。
6. 写内容、路径映射、观察、接受事件和绑定；条件更新使用原 expected，不用刚读取到的 current 重新生成 expected；核对受影响行数。
7. 同一个历史成功请求迟到时，仅返回历史结果，不能将已推进的当前指针倒回旧事件。任何失败由所属事务回滚全部新事实。

### 3. 统一验证器的边界

- `bind_archive_path` 不能只检查 acceptance_id 存在；必须确认接受的 path/asset/revision/content 与待绑定值一致，必要时包含根约束。
- `record_path_acceptance` 与维护审计共用 expected 的语义。现有“被替代内容必须为更旧代次”若保留，就在写前检查；若改为接受事件链，则同时改写读审计，不留旧条件。
- `load_content_binding` 不应在串错 acceptance 时返回另一文件的物理身份。局部加载校验精确关联，不必每次全库审计。
- 保留接受事件追加历史，禁止通过覆盖旧 acceptance/check 或把 acceptance_id 清空来解决冲突。

### 4. 必须逐一覆盖的反例

| 场景 | 期望 |
| --- | --- |
| 旧 A/BBBB 决议暂停，B/AAAA 同名替换已确认，再提交旧决议 | 拒绝；B 的接受/内容与全表不变 |
| 旧 REUSE 晚于同内容物理替换 | 拒绝或返回已处理历史结果；不回退物理身份 |
| 相同内容跨 root revision 的陈旧请求 | 令牌不匹配，不能写回旧根 |
| BASELINE / REUSE / NEW_REVISION / REPLACEMENT 重试 | 同事实返回首次接受，不新增行，允许调用时间不同 |
| 同 check ID，不同 run/time/hash/size/identity/root | 先比事实，结构化拒绝；不得被快速返回吞掉 |
| 历史成功请求在新接受后重放 | 返回旧操作结果且当前指针不变，或明确定义的无副作用冲突 |
| B 绑定传 A 的 acceptance_id；同路径其他代次 acceptance | 写前拒绝；load/audit 判定一致 |
| acceptance expected 自己、未来代次、其他资产 | 按冻结协议拒绝，不能先提交后靠维护审计发现 |

GitNexus 本轮在冻结树报告 `apply_content_resolution` 为 MEDIUM，11 个直接引用；实际调用还包括仓库分派和多份测试。下一位修改者仍须在自己的最终基线上刷新影响分析，不能拿本数字免检。

## R2：多路径与资产级历史，别名不能只修一层（AR4-04/05）

先决定：同物理对象的两个路径是同逻辑资产的两个位置，还是两个逻辑条目共享 blob。当前设计选择前者，不能只实现首次硬链接复用而忽略后续分叉。

若保留该选择，需明确资产历史头与路径接受的区别：A 已见 revision 2、B 仍指 revision 1，不代表 B 下一次必须写 revision 2。查找同资产的实际字节历史和分配新代次都要有事务重检；不要让全库“第一条相同摘要”替代该资产查询。

具体步骤：

1. 为滞后路径、改名后的已知物理对象、两个硬链接分别被替换制定解析结果。要么可解释地继续资产链，要么返回需确认的分叉/重新归属，不持续生成已占用键。
2. 资产代次分配与 R1 的 expected 重检一起考虑；MAX+1 仅是分配手段，不能证明两个对象应该属于同一资产。physical ID 可能复用，根映射也会变，不能当跨时间永久身份。
3. 文件名别名由实际目录项拼写/文件系统事实规范化，或显式 alias 映射。记录恢复路径的原始拼写；旧清单和旧 path_json 不覆盖。
4. 修改枚举/路径键之前列出 receipt/plan/source-kind/旧历史兼容方式。不改下载主线 `target_key` 去顺手“统一”；它有独立生产兼容风险。
5. 计划保存和 `_check_assets` 一起调整。仅允许 ensure 忽略 path_json 不够；不能通过改 `source_kind` 或丢弃历史原拼写绕过冲突。
6. 用同一个被接受样本跑 prepare→save→replay→close→load→maintenance audit 全流程，确认 alias 的各个入口判定相同。

验收至少包括：A/B 硬链接均 rev1，A→rev2 后 B 观察 rev3 字节；改写后改名；同字节他资产排在查询第一位；硬链接两侧独立替换；A→B→A；`A.bin/a.bin`；`画A.bin/画a.bin`；`画/A.bin/画/a.bin`；外部根 ID 大小写；NFC/NFD、straße/strasse；旧计划逐字不变。

## R3：唯一受控“观察接受 + 计划保存”应用命令（AR4-02）

**计划保存影响图为 HIGH**：本轮 2 个直接引用、52 个受影响符号，包含公开 wrapper、仓库分派、计划及历史审计测试。下一轮先复核实际调用，再改契约和所有入口，不让另一个分支同时修改此文件。

当前 `prepare_observed_plan` 是有价值的纯转换器；`apply_archive_resolutions` 是有价值的原子接受命令。继续复用两者，补一层明确的应用工作单元，不另造多个互相竞争的入口。

建议边界如下：

```text
有界枚举 + receipt
  → 事务外实际观察
  → 读取绑定令牌 / 解析 / 确认结果
  → 冻结输入（包括观察、expected、范围与批次预算）
  → writer: BEGIN IMMEDIATE
      重新验证 expected 和输入事实
      以统一幂等语义接受整批
      保存对应 planned 清单及不可变引用
      全部 COMMIT；任一步失败全部 ROLLBACK
  → 关闭重开，验证原始事实和旧计划
```

另一种可接受设计：纯计划保存绝不改变当前绑定，接受另有命令；但必须在应用层明确定义失败恢复和验收状态，不能继续把“清单存在”当作本批观察已成功接受。优先采用一个事务方便首版证明。

关键点：

- 移除“revision 较大即可推进当前绑定”的旁路。所有当前绑定更新都经过 R1 契约；索引未观察计划仍可以存在，但等级必须明确。
- 元数据与摘要读取在写事务外；不要持 SQLite 锁读 500 GB 文件。打包阶段仍需重新验证内容，不能把入库时间当永远新鲜。
- receipt 的 snapshot/mtime/root 校验保留；run_id 是同一阶段还是两个独立阶段须写清，若不同就建显式关联，不悄悄覆盖原值。
- 确保命令内所有载荷冻结，规范嵌套 list；声明字节/条目/队列预算必须覆盖实际输入，而不只 path_keys。当前新命令未提供整批观察预算验证证据，接线时补齐，避免靠调用者自觉。
- 计划封存和云端校验尚未实现；planned 不生成 sealed/verified/releasable 宣称。

故障注入：内容插入、观察插入、接受插入、绑定更新、计划头/分段/包索引写入各阶段失败；检查所有相关表回滚及 writer 后续服务。冲突时不自动覆盖、不重试同一陈旧决议。
