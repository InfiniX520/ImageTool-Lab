## N1：明确逻辑资产、内容和路径的关系（AR3-01 / 05）

主要范围：`archive_schema` 的查找与绑定、`archive_scope` 的解析器、必要的持久化契约；先写一页状态/键决定，再动 DDL。

### 必须先作出的设计决定

| 对象 | 稳定身份 | 允许复用 | 不允许推导 |
| --- | --- | --- | --- |
| 逻辑资产 | 已知作品/页身份，或明确分配的本地资产 ID | 同一逻辑对象的历史代次 | 两文件摘要相同所以是同一资产 |
| 内容代次 | asset_id + revision，事实不可变 | 原资产同版本、幂等重放 | 用另一资产某个 revision 替代当前资产 |
| 字节内容 | SHA-256 + 大小 | 存储/容量去重、相同字节统计 | 来源真实性、替换授权、逻辑资产所有权 |
| 路径绑定 | 受控根 + 可解释的规范路径 + 当前接受事件 | 已证明的同一目录项别名 | 只靠任意 Unicode casefold 合并文件 |
| 物理身份 | device/file_index + 本次范围和观察事实 | 当次候选交接、硬链接识别 | 跨时间永久不复用、全局逻辑 ID |

建议优先保持逻辑资产独立，摘要查找返回“相同字节存在”的证据，而不是另一资产的 ContentVersion。如果决定一个资产允许多个可分叉路径，必须明确版本分配和路径归属规则；不能只将 revision 改成 MAX+1 以掩盖资产合并。现有旧计划的 asset/revision/path 不改写。

### 路径具体处理

- 用真实目录项拼写和物理事实建立别名；PathRef 保留安全路径约束，显示和恢复拼写保持可解释。
- 同一次扫描的别名去重与跨次重选需使用同一规则。当前“同时选择能去重，分两次却生成不同键”必须消除。
- 已有资产 REUSE 时，不能因调用者大小写不同就尝试改写不可变 path_json；也不能悄悄覆盖历史拼写。需要规范路径或显式别名记录。
- 根 ID 的 ASCII 规范化应在注册/构造边界固定，不让键折叠、JSON 不折叠造成另一组冲突。
- 不改下载主线 `target_key`，除非单列兼容设计和原下载器回归。NFC/NFD、straße/strasse、硬链接各恢复路径必须保留。

验收矩阵：两个独立同字节文件分别改写；复制文件后独立演化；硬链接修改；内容 A→B→A；A.bin/a.bin；画A.bin/画a.bin；画/A.bin/画/a.bin；根 ID 大小写；不同 Unicode 文件；旧计划跨次重开不变。每个正向都检查最后路径绑定、全部历史行和恢复路径，而非仅“不抛异常”。

## N2：原子应用、真实 expected-old 和接受事件（AR3-02 / 03）

主要范围：`apply_content_resolution`、`bind_archive_path`、`load_content_binding`、仓库新增的专用命令。不得修改生产 `_enqueue` 以偷渡未声明载荷。

### 建议的写入顺序

1. 写事务开始，要求 `conn.in_transaction`。公开仓库命令统一开启事务；低层纯 SQL 适配器无事务立即拒绝。
2. 读当前 binding，严格比较解析输入中的 expected：包括“预期不存在”和“预期为特定版本/绑定代次”。先比较，后插行。
3. 对替换确认检查其绑定对象：确认针对哪个路径、旧内容/物理对象、新候选、根版本。不能用无限有效的全局 `True` 静默接受另一个候选。
4. 插入不可变内容与资产映射，按操作 ID/观察 ID 处理幂等。观察、接受事件和新绑定同事务提交；任何错误整批回滚。
5. 用 expected 作条件更新，检查受影响行数。不要把刚读到的 current key 当 expected 传回去。
6. 发生并发冲突返回结构化“重新解析/重新观察”，不自动采用更大的 revision，不覆盖新绑定。

### 接受与诊断必须分开

当前 binding 应显式指向最后接受的物理证据/事件，含 root_revision、内容版本和确认信息。观察流水可以先独立保存，但它不修改接受指针。`load_content_binding` 不再通过“按路径取最新一条非空 identity”猜测认可对象。

不要简单过滤 status=hash_match：初次基线是 unknown，已确认的内容替换可能是 changed。是否接受是一条独立事实，不能从诊断状态反推。

### 必测交错

| 次序 | 结果 |
| --- | --- |
| 解析时不存在，提交前另一命令已建立绑定 | 原结果拒绝，现有绑定不变 |
| 两命令都基于同一旧版本，内容不同 | 只允许符合当前 expected 的一条成功 |
| 同一 operation/同一事实重放 | 可解释的幂等，不增加历史事实 |
| 同一 ID/不同事实 | 冲突拒绝 |
| 记录 replaced/changed 检查但未确认 | 仍要求确认 |
| 旧根检查晚于新根检查写入 | 不改变当前根的认可物理身份 |
| autocommit 连接调用 apply | 写入前拒绝，全部表计数不变 |
| 内容插入、观察插入、绑定更新、计划写入各点失败 | 整批回滚，writer 可继续服务 |

使用真实两连接/子进程场景覆盖锁和交错；保留本轮不改 resolution 的自然交错反例。故障注入与正常工作流分别记录，不能只测一个手工坏参数。

## N3：一个实际可调用的离线交接入口（AR3-04）

当前已新增 `archive_observed_plan` 纯转换入口，继续复用它，避免再写第三套入口。它负责 ContentResolution→清单/容量/计划，不读取观察、不调用 writer；两个合法结果错配时还会把新摘要绑定到旧 snapshot/mtime。完整应用交接仍需补齐，旧根观察也不能被重新标注。先做能在合成根/临时库中调用的应用入口，不急着接 GUI、扫描真实图库或增加另一个 CLI。

建议流程：

```text
显式 root registry / revision / selection
  → 有界范围枚举与完整/未完整 receipt
  → 对候选实际只读观察（队外 I/O）
  → 原始证据与候选逐字段核对
  → 解析建议 + expected binding + 替换确认状态
  → 纯清单与容量
  → 唯一 writer 在一个有界事务中重核 expected 并保存事实/绑定/计划
  → 独立重开核对
```

不要把摘要读取移入数据库长事务。观察之后文件仍可能变化，计划只表示某时刻的观察；未来封包前需再次验证/稳定读取，释放前需另行验收。不能靠本次 receipt 宣称以后磁盘永远不变。

必须验证原始 evidence.root_revision 等于候选/当前根，不能在 `rebind_observation` 用 candidate 的值替换旧值。run_id 如果有“扫描会话”和“观察批次”两种含义，字段名和关联需明确；观察必须属于这次允许的交接，而不是只比 path。

`prepare_archive_plan` 保持纯函数可以，但要区分用户声明的计划和已观察计划。调用者给一个看似合法的 SHA-256 不是读取证明。面向正式流程的入口必须要求观察/解析记录；低层未验证计划如继续保留，标记清楚并限制后续可用操作。不要加 HMAC、随机 nonce 或更多布尔字段来替代缺失的关系检查。

退出条件：真实合成文件通过该入口完成首次、重复、改写、替换待确认、确认后继续、取消、冲突与重开；测试代码不再直接调用一串 DB helper 代替应用服务。此时再评估生产接线，而不是把服务未接 GUI 误写为“算法故障”。

## N4：数据库规模成本（AR3-06）

N1/N2 先定查询语义，再补索引。至少审查：

- 按摘要/大小的内容查找；是否仍需要查所有逻辑资产。
- 按路径的 owner/current binding 查找。
- 按路径/根版本/接受事件的观察关联；不能继续靠全表时间排序。
- 批量保存前重复的逐资产查询与可能的长事务。

以 `EXPLAIN QUERY PLAN` 和 SQLite VM 指令/访问次数为主要增长证据，墙钟和 tracemalloc 为辅助。测 100/200/400、2,000 文件、固定新批次+逐渐变大的历史库；同时包含摘要命中/未命中、重复内容和多历史版本。阈值根据实际访问方式制定，不用固定毫秒在不同机器上假失败。

DDL 改动要有明确 schema/实验格式策略：临时库版本迁移、旧版拒绝和新备份可重开分别验证。不能加索引后继续宣称所有旧 schema-3 库原样兼容；`_check_existing_objects` 对对象定义是严格比较。

## N5：合并后的异常契约及协议回归（AR3-10；AR3-07/08 保持关闭）

先修 AR3-10：共享 writer 已抛 LibraryBusyError，archive 保存边界须识别并按稳定协议返回，保留原始 cause；SQLite BUSY/LOCKED 可重试与 I/O/损坏/约束错误严格区分。不得新增自动无限重试。用真实持锁连接测两个仓库接口，不能只测试 `_translate_busy_failure` 本身。

收尾提交已修非 planned 校验和 checkpoint busy，独立反例也确认拒绝，不要重做已经完成的修复；保留原反例作为回归。继续把“不可变计划协议解码/验证”和“允许何种操作的状态判断”拆清楚。所有持有该格式计划的批次都应验证不可变部分；已完成/取消/失败状态不能变成空 receipt 的逃生通道。未来 sealed 包的数据与 planned 索引不同，应有各自状态校验，不能为了复用 `_load_in_transaction` 强行把所有状态改回 planned。

协议矩阵至少覆盖：null/坏 receipt、重复 JSON 键、缺段/多段/摘要不符、超大单段、超大 header、清单条目上限、总载荷上限、根版本、来源标签、artifact 路径、非法 created_at、部分清单计数和完整/子批关系。prepare、save、replay、read-only load、maintenance audit、schema-copy inspection 要对同一协议作出一致判定；不允许通过改变 state 绕开。

WAL 修复应区分三件事：事务已提交、活库可读、主文件已独立化。检查 checkpoint 返回值；busy 时给出可恢复状态，保留 WAL/SHM 和验证过的备份，不删除任何日志强行清理。必要的独立交付副本用 SQLite backup 产生并重开核验。长读事务释放后只做有界重试，不能再次从 v1 迁移或覆盖原备份。

验收含本轮保持旧读快照的真实反例；重新运行最终版 F6 核心场景：提交前终止、提交后未关闭、WAL 溢出、同批重放、并发冲突、busy 退出、迁移前后备份与重开。旧 `4a9c3f3` 的 61 项记录只作历史，不伪装成本轮结果。

## 三并发该怎样安排

这次并非完全没有 worktree：现场确有 F5、最终审查、busy、两个 AR2-04 方向的隔离树。问题在于**隔离之后缺少明确的共同基线、接口约定和最终合并验收**。本轮不能凭现场直接断言之前所有代理共改同一个文件；能确定的是主工作树在审计中持续变化，若干报告绑定旧 HEAD，busy 改动合并后破坏了另一模块的异常契约。

### 适合下一轮的三路分工

| 角色 | 工作 | 可写范围 | 合并时机 |
| --- | --- | --- | --- |
| A：身份/事务实现者 | N1→N2，连续串行处理同一状态机 | 事先列出的 archive_schema/archive_scope 相关符号和对应测试 | 设计约定冻结后分包提交 |
| B：独立反例/测试者 | 在同一冻结基线复现 AR3，准备行为断言、边界矩阵和 SQL 成本证据 | 自己 worktree 的专用测试文件与 runtime；不碰 A 的源码 | 先提交可在旧版失败的测试，再对 A 的具体 commit 复测 |
| C：可独立工作者 | 先修 AR3-10 的边界适配，或整理闭合问题和版本矩阵 | 本包明确的 archive_repository 与专用接口测试；不改 A 的 schema/解析器 | 单独审阅后由主代理整合 |

N3 的完整交接依赖 N1/N2，N4 索引依赖最终查询语义；不能为了凑三路，让三个代理同时改 archive_schema、版本协议或同一状态机。空出来的路可以读审、补反例、测增长，不必每路都写产品代码。主代理负责集成与当前文档，不能让多个代理同时改 TASK_PLAN/LOG 或切换主工作树分支。

### 每份任务单必须包含

```text
base_commit: 完整 SHA，所有角色明确知道自己基于哪版
worktree / branch: 独立绝对位置与分支，禁止共享源码工作树
goal / non_goals: 具体退出条件与本包不承担的能力
allowed_files_and_symbols: 文件/符号所有权；共享契约唯一负责人
input_output_contract: 类型、状态、异常、事务归属、schema/plan/receipt 版本
tests: 反例名、真实流程、必须保留的旧行为
evidence_dir: 本批下该角色专属目录，不与另一角色同名
handoff: commit SHA + diff 列表 + XML + 源码摘要 + 已知失败/未验证
integration: 主代理单独审阅、顺序合并、接口联测、最终完整回归
```

禁止说“在差不多的当前树上已通过”。B/C 改动若基于更老提交，要先检查依赖和版本差异；主代理接收具体提交，不复制一整个目录覆盖已有代码。发现重叠归属先由主代理调整任务，而不是让模型各自猜最终合并策略。

### 主代理的合并退出条件

1. 分支 diff 在约定范围内；不存在顺手带入别人的未提交修改。
2. 针对跨模块边界跑测试：本次真实例子是 writer 错误翻译→archive catch、candidate snapshot→receipt、resolver expected→DB 当前绑定。
3. 最后一次合并后，在同一冻结树跑专项和全量；旧树报告只留历史，不直接累加成“最终通过数”。
4. XML、manifest、HEAD、当前计划四者绑定一致；若工作树又改变，停止验收结论，重新锁定范围。
5. 所有代理退回 idle/finished、worktree 状态已记录后，才做归档整理。先保存分支/补丁/manifest；不删除有未提交代码的 worktree，不强行 prune。
