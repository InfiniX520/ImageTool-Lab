版本：v1.3，2026-10-24。E1-2 独立工具已实现并完成有限真实验收；当前入口见 [CLI 说明](../../../ORGANIZER_CLI.md)，证据见[本轮记录](../../../../docs/maintenance/2026-10-24_jpgpng_organizer_cli.md)。E1-3 分类小样与 E1-4 大批量整理尚未完成。第 2、7、8 节保留 E1-1 当时的证据和未知项，最新实现边界见第 9 节及[实施进度](../REFACTOR_PROGRESS.md)。

## 1. 用户目标与产品边界

用户希望由 AI 查看关注画师的多张作品，整理真实 Pixiv 账号里的关注分组；整理后由用户在 Pixiv 网站查看和调整。用户过去通常浏览十几张作品后才决定关注，单张作品或仅靠名字、标签不能代表画师。

已确认的目标与约束：

- 整理工作由 AI 承担。CLI 提供读取作品、分组操作和进度工具，画面判断由能实际查看图片的 AI 在整理任务中完成。
- 交付落点是 Pixiv 账号中的分组。本地清单只作过程记录，不能冒充网站整理已经完成。
- 尊重用户已有的关注选择，分类用于查找和管理画师；本功能不根据 AI 的喜好自动取关、增关或修改关注公开性。
- 用户可以随时在网站调整；下一轮整理应识别并保留这些修改。
- 原图质量、下载性能优先。下载界面保持无预览；整理任务的作品采样独立、按需执行。
- E1-0 按用户明确的“第 1 项：加入重构计划”完成；后续工作按具体任务范围推进，独立扩展不自动改变主线状态。用户后续另行明确从 P3 恢复下载器主线，实际状态见实施进度。

工程基线：放在 JpgPng 内作为独立工具，复用现有 Python 环境、可共用的认证与请求基础设施；新增运行依赖目标 0，业务路径相对项目根定位。首版不另建看图 GUI、Node 工程、本地模型环境或无人值守 AI 服务。模块位置、命令名和接口结构在 E1-1 通过后再定，本文不提供未经验证的可执行命令。

## 3. 计划中的整理流程

### 3.1 读取账号现状

读取当前账号身份、关注清单、已有分组与成员关系，区分公开/非公开可见范围并核对分页完整性。以稳定画师 ID 关联记录，改名和换序不视为新画师。快照不完整时保留未知范围，不据此删除或重建原分组。

先保留原有分类，再根据用户查找画师的方式提出分类规则。题材/IP、画风或使用场景都只是候选维度；具体名称、数量和多组归属方式须结合网站能力及小样结果确定，不在本计划中代定。

### 3.2 多图取样与实际查看

- 初始设计基线为每位画师约 12～20 张，尽量来自不同作品，并覆盖近期与较早作品；不是用户指定的硬性配额。
- 多页作品按判断需要补看，避免同一作品的十几页占满样本后误称已覆盖作品集。画风或题材混杂时补看，记录采样范围和原因。
- 优先获取足以判断构图、题材和风格的中等尺寸图片，细节不足再查看较大版本；样本与正式原图下载库分开。
- 作品少于基线时查看实际可用作品并说明范围。不可访问、图片读取失败、作品类型暂不支持或样本不足时保留待复核，不以文字标签补写“已看图”。
- 元数据和简介只作辅助。记录实际看过的作品 ID、页号、作品日期/取样位置、简短判断依据、分类规则版本，以及是否需要补看。

571 位画师每位 12～20 张约为 6,852～11,420 张样本，仅用于说明量级，不是本次执行预算或完整覆盖承诺。后续按批设置画师数、请求数、图片字节和时间预算，耗尽后保存进度。

### 3.3 分类与写回

AI 基于已实际查看的作品生成分类建议和简短理由；不确定项单列，可补看或暂缓。分类不等于重新判断用户应不应该关注，也不能仅因最新几张题材相同就断定画师只画该题材。

写回前形成可核对的改动清单，包含画师 ID、原分组、目标分组和依据。后续实际任务按已明确的分类规则与批次范围执行，不需要用户逐个替 AI 整理。当前只规划，尚未确定具体分类规则或账号改动清单。

每项写回后读取网站现状确认；接口返回成功但读回不一致时保留未确认状态。只有网站实际结果已核实才计为完成。写入超时先核对是否已经生效，不盲目重复请求；无法核对时停在待确认位置。

### 3.4 网站调整与续跑

Pixiv 当前分组是用户使用的权威结果。本地同时保留采样进度、建议、写前快照与已确认写回记录，不能把较早的本地建议强行覆盖到网站。

下一次写回前比较当前网站状态与上次快照：已被用户修改的画师、已改名/删除的分组进入冲突记录，保留现状；不自动创建回用户删掉的组。仅对仍符合本轮前提的对象继续执行。

恢复以账号 ID、画师 ID、实际分组标识和操作记录定位，不靠列表序号。若网站没有稳定分组 ID，身份映射及改名识别属于 E1-1 必须验证的限制。补偿撤销只针对本工具已确认执行的改动，先比对当前状态；不整批覆盖快照，不承诺网站不支持的事务式回滚。

## 4. 与下载器、数据和资源的关系

- 下载器启动、切页、查看名单和普通下载不触发整理采样，也不承担作品预览的解码工作；整理工具不向正式下载账本写入样本“下载完成”记录。
- 整理正式实现排在 P3/P4/P5 的原图交付、关注闭环和性能门槛稳定之后。首版整理请求与下载批次错开，核对账号级请求预算，避免独立进程叠加请求而影响下载。
- 样图按批获取、复用已缓存内容，资源有上限；下载成功、AI 实际查看、建议形成、账号写回确认分别记录，中断后只续接未完成步骤。
- 正式整理进度、写前快照和变更记录属于业务资料。落地时为其确定项目内独立目录并登记到工作区保护清单；可再生成的样图另行管理，不能把恢复记录一并当缓存清理。
- `.runtime/` 只存隔离验证样本与报告；E1-0/E1-1 不创建正式数据目录、数据库、凭据副本或修改保护清单。凭据沿用适用的既有保密约束，日志和导出不含 Cookie/Token。
- 后续按组下载通过读取网站成员快照、解析稳定画师 ID，接入现有任务与筛选契约。已创建任务的范围保持不可变，网站后续调整在新任务中重新读取；多组重叠时按画师/作品身份去重，不改用户的原图、多页和筛选设置。

## 8. 已验证协议与后续实现约束

### 8.1 读取与写回

下表来自维护前网页自身代码及真实请求。路径以 Pixiv 站点为基准，不能直接当作不需要登录的公共 API。App API 用既有配置的凭据读取作品；分组验证在已登录网页内执行，同源会话和 CSRF 校验值始终留在浏览器，未导出到命令行或报告。

| 能力 | 请求与必要业务参数 | 本次证据 |
| --- | --- | --- |
| 关注列表/分组目录 | GET `/ajax/user/:account_id/following`；`offset`、`limit`、`rest=show/hide`、`tag` | 公开/非公开总数与目录已读取；带分组名可只列该组画师 |
| 一位画师的分组状态 | GET `/ajax/following/user/details`；`user_id` | 返回 `user_id`、`restrict`、`tags`；分组选中状态需看每项 `selected` |
| 加入分组 | POST `/ajax/following/user/tag_add`；表单 `user_id`、`tag` | 新组和画师关系已创建并读回确认 |
| 分组改名 | POST `/ajax/users/follow_tags/rename`；表单 `tagName`、`newTagName` | 仅含测试画师的组改名后，成员不变，名称读回一致 |
| 从分组移出 | POST `/ajax/following/user/tag_delete`；表单 `user_id`、`tag` | 成员已移出；本次最后一位成员移出后，该组从目录消失 |
| 显式删除整个组 | POST `/ajax/users/follow_tags/delete`；表单 `tagName` | 只确认网页代码定义，未调用；不能标作实际验收通过 |

三次写请求均为表单编码，使用浏览器当前请求校验值。HTTP 200 及 `error=false` 后仍另发 GET 核对成员与目录；成功判定不能只看 POST 返回。

### 8.2 数据和分类约束

- 本次接口以名称标识分组，未发现需要采用的稳定组 ID。正式工具以账号和名称快照处理改名/删除冲突，不能用本地旧名称自动覆盖网站变化。
- 画师详情的 `tags` 是带 `name`、`selected` 的对象列表；不能把所有可选组都当作该画师已加入的组。列表接口的 `followUserTags` 则是名称列表。
- 当前网页前端限制每位画师最多选 5 组，名称长度按 JavaScript `length` 不超过 20。5 指画师选中组数，不是整个账号最多 5 组；这次没有做服务端极限测试。
- 空分组结果的 `total` 本次返回字符串 `"0"`，非空时返回整数。解析时只接受非负整数或对应整数字符串，不能因类型差异误报恢复失败，也不能把错误结果当空组。
- 本次只测试一位画师和一个临时组，不证明全量盘点、批量并发、重复写入、写入超时、人工修改冲突等已通过。

### 8.3 关机及维护后恢复

验证用 PowerShell/DevTools 入口记录了当时的 Chrome PID，页面内的预检、已尝试写入等标志也只在内存中。关机后这些信息无效，不能直接重放旧写脚本或根据历史 HTTP 200 跳过当前预检。

正式入口必须重新定位目标标签页，核对源站、账号和会员能力，再读取当前关注关系/分组；写前意图及读回结果需持久保存。CLI 应以一个受控批次调用这些动作，避免人工逐条复制控制台命令；这是 E1-2 的实现目标，不能把本次临时入口说成已交付的通用 CLI。

维护期间进入等待恢复状态，保留样图、意图与历史读回记录；不反复登录、刷新接口或把维护错误当作凭据失效。服务恢复后先做一次有限的只读预检，核对网站现状；未知写入先查结果，再决定继续或补偿。新任务从当前网站状态出发，尊重用户在关机前后的手动调整。

## 9. E1-2 实现决定与交付边界（2026-10-24）

- 入口 `organize.cmd` / `organize.py`，模块 `organizer/`，业务资料 `organizer_data/`；路径相对项目根，默认使用工作区既有解释器，新依赖 0。下载器 UI 与普通下载不承担样图工作。
- 复用可聚焦的已登录 Chrome，通过 Windows UI Automation 提交页内同源命令，账号与会员每次核对；认证秘密留在浏览器。以仅保留一个本工具结果字段替代增长的控制台扫描，不清除浏览器原日志。
- SQLite journal 使用 FULL/WAL，操作意图先持久化；计划与审阅不可变，逐项写回后另行读取。unknown/intent 先 reconcile，未生效或冲突需重新规划；不重放旧脚本。默认叠加分组，替换须显式指定。
- 快照读取两种可见性、目录和每组成员，保存完整性与动态网站非原子属性；真实账号本轮为 602/0，目录为空，非空分组的完整分页故障场景由离线测试覆盖。
- 默认 16 个不同作品，按 ID 新旧范围取样并记录实际日期，多页可补看；AI 必须实际查看并声明，至少 12 个不同作品或说明画师实际作品较少。证据不足 needs_more=true，不进入计划。本轮 4 图只验证交接，不代表完成分类。
- 默认每命令 80 请求、32 MiB、600 秒，串行且至少 0.5 秒间隔；缓存上限 512 MiB/20,000 项，单图 8 MiB，每样本 40 图。没有自动淘汰历史证据。分页与样本可续跑，样本命中须核验摘要。
- 写回只实现加组/移出；组改名、整组删除、取消关注和改变公开性均无命令。可生成已确认变更的补偿计划，须比对现状且显式执行。未知服务端极限、网站并发事务和大批性能不做超出证据的承诺。
- 新版下载器与网络整理命令共用锁；旧版需先关闭。按组下载适配和分类规则校准仍是 E1-3/E1-4 的后续事项。

具体命令、错误恢复、备份与已知限制以 [CLI 说明](../../../ORGANIZER_CLI.md) 为准；验收 89 项相关离线、15 项页内协议、真实盘点/图片/两次已补偿写回，均见本轮维护记录。没有把 F01—F10 所有后续场景统一标作已经完成。
